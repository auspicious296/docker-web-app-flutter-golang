# Go（Golang）セットアップ手順書（macOS 向け）

本プロジェクトのバックエンド API を開発するために、macOS へ Go と DB マイグレーションツール golang-migrate をインストールする手順です。
Go を初めて使う方を対象としています。

Go のバージョンを管理したい場合や、開発チーム全員でバージョンを揃えたい場合は、「[3. Go のバージョンを管理・統一する方法](#3-go-のバージョンを管理統一する方法)」を参照してください。

- 対象 OS: macOS（Apple Silicon / Intel 共通）
- 対象シェル: zsh（macOS の標準シェル）
- インストールするバージョン: Go 1.27.1、golang-migrate 4.20.1

---

## 1. 手順

### 手順 0. すでにインストールされているか確認する

```bash
go version
```

**表示結果による分岐**

| 表示結果 | 対応 |
|---|---|
| `go version go1.27.1 darwin/arm64` のように表示される | インストール済みです。手順 4 へ進んでください |
| `zsh: command not found: go` と表示される | 未インストールです。手順 1 へ進んでください |
| 1.27.1 より古いバージョンが表示される | 手順 2 の更新コマンドでバージョンを上げてください |

### 手順 1. Homebrew があるか確認する

```bash
brew --version
```

`Homebrew 4.x.x` のようにバージョンが表示されれば準備完了です。
`command not found` の場合は、先に [Homebrew 公式サイト](https://brew.sh/ja/) の手順でインストールしてください。

### 手順 2. Go をインストールする

```bash
brew install go
```

すでに古い Go が入っている場合は、代わりに以下を実行します。

```bash
brew upgrade go
```

### 手順 3. インストールできたか確認する

```bash
go version
```

```
go version go1.27.1 darwin/arm64
```

上記のように表示されれば成功です（`arm64` の部分は Intel Mac では `amd64` になります）。

### 手順 4. Go が参照する場所を確認する

```bash
go env GOROOT GOPATH
```

```
/opt/homebrew/Cellar/go/1.27.1/libexec
/Users/ユーザー名/go
```

2 行表示されれば正常です。

### 手順 5. PATH に Go のツール置き場を追加する

以下のコマンドを実行し、設定ファイルに 1 行追記します。

```bash
echo 'export PATH="$PATH:$(go env GOPATH)/bin"' >> ~/.zshrc
```

追記した内容を現在のターミナルに反映させます。

```bash
source ~/.zshrc
```

反映されたか確認します。

```bash
echo $PATH | tr ':' '\n' | grep go
```

`/Users/ユーザー名/go/bin` が表示されれば成功です。

### 手順 6. 動作確認する

作業用の一時ディレクトリを作成し、移動します。

```bash
mkdir -p ~/tmp/go-hello && cd ~/tmp/go-hello
```

モジュールを初期化します。

```bash
go mod init example/hello
```

サンプルプログラムを作成します。

```bash
cat > main.go << 'CODE'
package main

import "fmt"

func main() {
	fmt.Println("Hello, Go!")
}
CODE
```

実行します。

```bash
go run .
```

```
Hello, Go!
```

上記が表示されればセットアップ完了です。

確認用ディレクトリは不要なので削除します。

```bash
cd ~ && rm -rf ~/tmp/go-hello
```

### 手順 7. golang-migrate をインストールする

```bash
brew install golang-migrate
```

インストールできたか確認します。

```bash
migrate -version
```

```
v4.20.1
```

上記のように表示されれば成功です。

PostgreSQL 用のドライバーが組み込まれているか確認します。

```bash
migrate -help 2>&1 | grep "Database drivers"
```

表示された一覧に `postgres` が含まれていれば準備完了です。

## 2. 各手順の解説

### 手順 0 ─ なぜ最初に `go version` を実行するのか

`go version` は「Go が入っているか」と「入っているならどのバージョンか」を同時に確認できるコマンドです。

macOS には Go が標準で入っていません。しかし、過去に別のツールが依存関係として Go を入れていることがあり、その場合は古いバージョンが残っています。二重インストールによる混乱を避けるため、まず現状を把握します。

表示される `darwin/arm64` は「macOS 用 / Apple Silicon 向け」を意味します。Go はビルド時に OS と CPU の種類を指定できる言語のため、バージョン番号とセットでこの情報が表示されます。

### 手順 1・2 ─ なぜ Homebrew を使うのか

Go は [公式サイト](https://go.dev/dl/) から `.pkg` インストーラをダウンロードする方法もありますが、本手順書では Homebrew を採用しています。理由は以下の通りです。

| 観点 | Homebrew | 公式インストーラ |
|---|---|---|
| バージョン更新 | `brew upgrade go` の 1 コマンド | 毎回サイトから再ダウンロード |
| アンインストール | `brew uninstall go` で完全に削除 | 手動でファイルを消す必要がある |
| 他ツールとの管理 | Docker などと同じ方法で一元管理できる | Go だけ管理方法が別になる |

また、本プロジェクトで採用する Go 1.27.1 は、現時点の Homebrew が提供するバージョンと一致しているため、`brew install go` でそのまま目的のバージョンが入ります。

### 手順 4 ─ `GOROOT` と `GOPATH` とは何か

Go には役割の異なる 2 つのディレクトリがあります。混同しやすい部分なので、違いを押さえてください。

| 環境変数 | 指す場所 | 中身 | 誰が使うか |
|---|---|---|---|
| `GOROOT` | Go 本体のインストール先 | コンパイラ、標準ライブラリ | Go 自身が使う。開発者は触らない |
| `GOPATH` | 作業用ディレクトリ | ダウンロードしたライブラリ、インストールしたツール | 開発者が間接的に使う |

**`GOROOT` は設定不要です。** Homebrew でインストールすると自動的に正しい場所が設定されます。手動で設定すると、バージョン更新時に古い場所を指したままになり不具合の原因になります。

**`GOPATH` は既定で `~/go` です。** この配下には以下が作られます。

```
~/go/
├── pkg/mod/    # ダウンロードしたライブラリの実体（キャッシュ）
└── bin/        # go install で入れたコマンドの実行ファイル
```

かつての Go（1.11 より前）は、開発するソースコード自体も `GOPATH` の配下に置く必要がありました。現在はモジュール方式（後述）になったため、**プロジェクトは好きな場所に置けます**。古い解説記事では「GOPATH 配下で開発する」と書かれていることがありますが、現在は当てはまりません。

### 手順 5 ─ なぜ PATH に追記するのか

Go では、開発を補助するツール（コード整形、Lint、マイグレーションツールなど）を `go install` コマンドで導入します。これらのツールの実行ファイルは `~/go/bin` に置かれます。

しかし macOS は、PATH に登録された場所からしかコマンドを探しません。`~/go/bin` は既定では登録されていないため、ツールを入れてもコマンド名だけでは実行できず、`~/go/bin/ツール名` とフルパスを打つ必要があります。

この不便を解消するため、`~/.zshrc`（ターミナル起動時に毎回読み込まれる設定ファイル）に PATH への追加を書いておきます。

なお、`go` コマンド自体は Homebrew が `/opt/homebrew/bin` に配置し、そこは最初から PATH に入っているため、追加設定は不要です。

### 手順 6 ─ `go mod init` と `go run` とは何か

**`go mod init` ─ モジュールの初期化**

Go では、1 つのプロジェクトを「モジュール」という単位で扱います。`go mod init example/hello` を実行すると、以下の内容の `go.mod` ファイルが作られます。

```
module example/hello

go 1.27.1
```

`go.mod` は「このプロジェクトの名前」と「使用する Go のバージョン」、そして「依存する外部ライブラリとそのバージョン」を記録するファイルです。他言語で言えば `package.json`（Node.js）や `pubspec.yaml`（Flutter）に相当します。

外部ライブラリを追加すると `go.mod` に自動で追記され、同時に `go.sum`（ライブラリの改ざん検証用のハッシュ値を記録するファイル）も作られます。この 2 ファイルがあれば、別のマシンでも `go mod download` で同じ依存関係を再現できます。

**`go run` ─ ビルドと実行を一度に行う**

Go はコンパイル型の言語であり、本来は「ビルドして実行ファイルを作る → それを実行する」という 2 段階が必要です。

| コマンド | 動作 | 用途 |
|---|---|---|
| `go run .` | 一時領域でビルドして即実行し、実行ファイルは残さない | 開発中の動作確認 |
| `go build -o ./bin/api ./cmd/api` | 指定した場所に実行ファイルを作る | 配布・デプロイ用 |

動作確認では手軽な `go run` を使いました。実際のアプリケーションのビルドでは `go build` を使い、成果物を明示的な場所へ出力します。

**なぜ `main.go` の中身がこの形なのか**

```go
package main       // 実行可能なプログラムであることを示す宣言

import "fmt"       // 標準ライブラリ fmt（書式付き入出力）を読み込む

func main() {      // プログラムの開始地点。この関数から実行が始まる
	fmt.Println("Hello, Go!")
}
```

Go では `package main` かつ `func main()` を持つファイルだけが実行可能なプログラムになります。この 2 つが揃っていないとライブラリ扱いとなり、`go run` できません。

### 手順 7 ─ golang-migrate とは何か、なぜ Homebrew で入れるのか

golang-migrate は、データベースのテーブル構造の変更（マイグレーション）を SQL ファイルで管理するツールです。本プロジェクトでは、`backend/migrations/` に置いた SQL ファイルを、このツールの `migrate` コマンドで PostgreSQL に適用します。

`migrate` コマンドは `go install` でも導入できますが、本手順書では Homebrew を採用しています。`go install` の場合は、利用するデータベースのドライバーをビルド時のタグ（`-tags 'postgres'`）で指定する必要があり、指定を忘れると PostgreSQL に接続できないコマンドが出来上がってしまうためです。Homebrew 版は PostgreSQL を含む主要なドライバーをすべて組み込んだ状態でビルドされているため、この指定が不要です。

`migrate -help` の出力は標準出力ではなく標準エラー出力に書き出される仕様のため、`2>&1` で通常の出力にまとめてから `grep` で絞り込んでいます。

### 補足 ─ インストール後に PATH が通らない場合

`brew install go` が成功したのに `go version` で `command not found` が出る場合、Homebrew 自体の PATH が通っていない可能性があります。以下を実行して確認してください。

```bash
ls /opt/homebrew/bin/go
```

ファイルが存在するのにコマンドが見つからない場合は、以下を `~/.zshrc` に追記し、`source ~/.zshrc` で反映させます。

```bash
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zshrc
```

Intel Mac の場合、パスは `/opt/homebrew` ではなく `/usr/local` になります。

## 3. Go のバージョンを管理・統一する方法

Go には、使用するバージョンを固定したり、開発チーム全員で揃えたりするための仕組みが**標準で組み込まれています**。Flutter における FVM のような外部ツールを別途導入する必要はありません。

### 3-1. 本プロジェクトでバージョンが決まる場所

まず、どこでバージョンが決まるのかを整理します。

| 場面 | バージョンを決めるもの | 状態 |
|---|---|---|
| コンテナ内でのビルド | `backend/Dockerfile` の `golang:1.27.1-alpine` | 誰がビルドしても同じバージョンになる |
| ローカルでの `go build` / `go run` | 各自の Mac に入れた Go（手順 2 の Homebrew 版） | 各自の環境に依存する |

コンテナ経由でビルドした成果物はイメージタグによってバージョンが固定されています。したがって、バージョンの統一を意識する必要があるのは、**ローカルで直接 `go` コマンドを実行する場合**です。

### 3-2. 方法 A ─ `go.mod` の `toolchain` による自動統一（Go 1.21 以降の標準機能）

`go.mod` に必要なバージョンを記載しておくと、`go` コマンド自身が、そのバージョンのツールチェーン（コンパイラ一式）を**自動でダウンロードして使用します**。

```
module backend

go 1.27.1

toolchain go1.27.1
```

この状態で `go build` / `go run` / `go test` を実行すると、手元の Go が古くても、Go が自動的に 1.27.1 のツールチェーンを取得し、そちらで処理を実行します。取得したツールチェーンは `~/go/pkg/mod/golang.org/toolchain@.../` に置かれ、Homebrew で入れた Go 本体は置き換わりません。

`go.mod` はリポジトリで共有されるため、**各自が手動でバージョンを合わせる作業が不要になります**。

本プロジェクトの `backend/go.mod` には、現在 `go 1.27.1` が記載されています。

**`GOTOOLCHAIN` 環境変数による挙動の制御**

この自動取得の挙動は、`GOTOOLCHAIN` 環境変数で制御します。

| 設定値 | 挙動 |
|---|---|
| `auto`（既定値） | `go.mod` の要求を満たさないときだけ、指定バージョンを取得して切り替える。手元の Go の方が新しければ手元のものを使う |
| `go1.27.1` | 常にこのバージョンを使う（完全固定） |
| `go1.27.1+auto` | 最低ラインを 1.27.1 とし、`go.mod` がより新しいものを要求すればそれに従う |
| `local` | 自動取得を無効化し、必ず手元にインストールされた Go を使う |

現在の設定と、実際に使用されるバージョンは以下で確認できます。

```bash
go env GOTOOLCHAIN
go version
```

完全に固定したい場合は、以下のように設定します。

```bash
go env -w GOTOOLCHAIN=go1.27.1
```

**注意点**

`go` 行と `toolchain` 行は「**最低限これ以上のバージョンが必要**」という意味です。既定の `auto` では、手元の Go の方が新しい場合はそのまま手元のものが使われ、ダウングレードはされません。バージョンを厳密に一致させたい場合は、上記の `go env -w GOTOOLCHAIN=go1.27.1` で明示的に固定します。

また、この仕組みが働くには、起動役として Go（1.21 以降）が 1 つインストールされている必要があります。手順 2 の `brew install go` がその役割を果たします。

### 3-3. 方法 B ─ バージョン別のコマンドを併存させる（`golang.org/dl`）

Go 公式が提供する仕組みで、特定バージョンを「別名のコマンド」として追加できます。複数バージョンを手動で使い分けたい場合に使います。

```bash
go install golang.org/dl/go1.26.5@latest   # ラッパーコマンドを追加する
go1.26.5 download                          # 本体をダウンロードする
go1.26.5 version                           # 動作確認
```

以後、`go1.26.5 build ...` のように、コマンド名でバージョンを指定して実行できます。

| 配置されるもの | 場所 | 役割 |
|---|---|---|
| ラッパーコマンド | `~/go/bin/go1.26.5` | 処理を本体へ受け渡す小さなプログラム |
| Go 本体一式 | `~/sdk/go1.26.5/` | コンパイラ、標準ライブラリ |

Homebrew で入れた `go` 本体や `GOROOT` には一切影響せず、**完全に分離されて併存します**。必要になった時点でいつでも追加でき、不要になれば以下の 2 つを削除するだけで元に戻ります。

```bash
rm -rf ~/sdk/go1.26.5      # 本体
rm ~/go/bin/go1.26.5       # ラッパーコマンド
```

同じ手順を繰り返せば、複数のバージョンをいくつでも並べられます。

### 3-4. 方法 C ─ サードパーティのバージョン管理ツール

FVM に最も立ち位置が近いのはこれらのツールですが、Go では方法 A が標準機能として用意されているため、使用頻度は高くありません。複数の言語のバージョンをまとめて管理したい場合の選択肢になります。

| ツール | 設定ファイル | 特徴 |
|---|---|---|
| `mise` | `.mise.toml` | Go 以外（Node.js, Python など）も一元管理できる |
| `asdf` | `.tool-versions` | 複数言語に対応。プラグイン方式 |
| `goenv` | `.go-version` | Go 専用。`rbenv` に近い操作感 |

### 3-5. 3 つの方法の比較

| | 方法 A（`toolchain`） | 方法 B（`golang.org/dl`） | 方法 C（サードパーティ） |
|---|---|---|---|
| 追加インストール | 不要（Go の標準機能） | 不要（`go install` のみ） | 必要 |
| チームでの共有 | `go.mod` を共有するだけで自動的に揃う | 各自が個別に実行する必要がある | 設定ファイルを共有し、各自がツールを導入する |
| 使い分けの方法 | 自動（`go` コマンドがそのまま使える） | コマンド名を変えて実行する | コマンドで切り替える |
| 主な使いどころ | チーム全員のバージョンを揃える | 特定バージョンでの動作を一時的に検証する | 複数言語のバージョンを一元管理する |
