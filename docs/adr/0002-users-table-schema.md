# users テーブルのスキーマ設計

ステップ 1-3 で作成する `users` テーブルについて、ロードマップの記載（`id` は `BIGSERIAL`、`email` に `UNIQUE`）から 4 点を変更・追加して決定した。**`id` は `BIGINT GENERATED ALWAYS AS IDENTITY`、`name` は `COLLATE "ja-JP-x-icu"` を明示、`email` の大文字小文字はアプリ側の小文字化で扱い DB は素直な `UNIQUE` のみ、削除は `deleted_at` による論理削除**とする。画面も API もまだ存在しないこの時点で決めたのは、いずれもデータそのものに残る決定であり、第二段階ではこのテーブルがログイン ID を兼ねるためである。

## 検討した選択肢

**`id` — `BIGSERIAL`（ロードマップの記載）** — PostgreSQL 公式 wiki が「Don't use serial」として新規アプリでの利用を非推奨とし、例外を PostgreSQL 10 未満・テーブル継承・複数テーブルでのシーケンス共有の 3 つに限定している。本プロジェクトはいずれにも該当しない。`serial` は採番を「列の既定値（`nextval()`）」として表現するため、①`INSERT` で `id` を明示するとシーケンスを更新せずに通ってしまい、後続の自動採番が主キー重複で失敗する、②登録処理にシーケンスへの `USAGE` 権限が別途必要になる、③`CREATE TABLE ... (LIKE ... INCLUDING DEFAULTS)` で複製すると複製先が元テーブルのシーケンスを共有する、という落とし穴を持つ。`IDENTITY` は採番を「列の属性」として扱うため、これらがいずれも生じない。`BY DEFAULT` ではなく `ALWAYS` を選んだのは、`id` を明示した `INSERT` そのものを DB に拒否させ、①の事故を防ぐためである。ロードマップと開発ガイドの `BIGSERIAL` の記述は、この決定に合わせて修正する。

**`email` — DB 側で大文字小文字を無視する（`lower()` の式インデックス / `citext` / 非決定的照合順序）** — 当初は `CREATE UNIQUE INDEX ... ON users (lower(email))` を検討したが、「入力どおり保存しつつ一意性の判定だけ大文字小文字を無視する」のは保存ルールと判定ルールが食い違う状態であり採用しなかった。Google は大文字を受け付けず小文字に変換して保存するため `lower()` での判定と整合するが、本アプリにその保存ルールを設けないなら、判定だけを緩める根拠がない。最終的に Google と同じく**保存前にアプリ側で小文字へ変換する**方針とし、DB には小文字のみが入る前提で素直な `UNIQUE` を置いた。非決定的照合順序（公式が `citext` より推奨する手段）は、`=` が自然に書ける代わりに性能ペナルティとパターンマッチの制約を負うため見送った。なお RFC 5321 は local-part を大文字小文字を区別して扱うことを MUST としつつ、その区別を利用することは相互運用性を損ねるため推奨しないと述べている。

**`name` — 照合順序を指定しない** — 実測の結果、この環境の DB は `en_US.utf8` と宣言されているものの、`postgres:18.6-alpine` の musl libc が照合順序を実装していないため、実際の並びは符号順だった（`A B a b` / `あ ん ア 亜`）。ユーザー一覧を名前順に並べる用途では実用に耐えないため、ICU の `"ja-JP-x-icu"` を列に明示する（`a A b B` / `あ ア ん 亜`）。この照合順序は決定的であるため、`=` や `LIKE` の挙動に制約は付かない。ただし**漢字は読み順には並ばない**（漢字自体が読みを持たないため、ICU でも同じ）。50 音順が必要になった時点で、カナの列を追加する必要がある。

**削除 — 物理削除** — CRUD の 4 操作を通すという教材上の目的には物理削除が最も単純だが、`deleted_at` を後から追加すると、第二段階のログイン照合を含む全クエリに条件追加が必要になるため、最初から論理削除とした。`email` の `UNIQUE` は「生きている行の中で一意」とする部分インデックスにはせず、素直な `UNIQUE` を維持する。退会したユーザーが同じメールアドレスで再登録する場合は、新しい行を作らず `deleted_at` を `NULL` に戻して既存の行を復帰させる方針とし、復帰日時の記録が必要になれば履歴用のテーブルを別途追加する。

**`updated_at` — DB のトリガーで自動更新する** — PostgreSQL には MySQL の `ON UPDATE CURRENT_TIMESTAMP` に相当する列の設定がなく（生成列も `now()` のような volatile な関数を使えない）、更新時に自動で時刻を入れる手段はトリガーだけである。トリガーを採用すれば `updated_at` は「行が最後に変更された時刻」となり pgAdmin からの直接更新も記録されるが、SQL のどこにも書かれていない箇所で値が変わるため、学習用テンプレートとしては挙動を追いにくい。`UPDATE` を書く箇所が限られることから、Go 側で明示的に `now()` を入れる方針とした。この決定はトリガーを追加するマイグレーションを 1 本足すだけで後から変更できる。

## 結果として生じること

- **`email` の一意性は DB では保証されない。** pgAdmin から大文字を含むアドレスを直接挿入すれば、大文字小文字だけが異なる重複が発生し得る。小文字化は Go 側の責務である。
- **取得系のクエリはすべて `WHERE deleted_at IS NULL` を必要とする。** 書き忘れると退会済みユーザーが一覧に表示され、第二段階ではログインも通ってしまう。
- **復帰したユーザーは `id` と `created_at` が初回登録時のまま残る。** また、この方式では「同じ人の復帰」と「別人による同一アドレスでの新規登録」を区別できない。
- **`updated_at` はアプリ経由の更新のみを記録する。** pgAdmin やマイグレーションでデータを直接修正した場合、値は更新されない。
- **`name` の照合順序は、DB イメージに ICU が含まれていることを前提とする。**
- `deleted_at` のインデックスと、空文字を禁止する `CHECK` 制約は現時点では設けない。いずれも必要になった時点で追加できる。

## 追記：ステップ 1-4 の仕様策定にともなう変更

ステップ 1-4（ユーザー管理 API）の仕様を固める過程で、本 ADR の内容に 4 点の変更が生じた。経緯は [0004-user-api-design.md](0004-user-api-design.md) に記録している。

**アカウントロック用の 3 列を `000002` で追加する** — 第二段階のログインで「5 回連続で失敗したらロックし、解除は管理者が行う」仕様を決めたため、`failed_login_attempts`（`INT NOT NULL DEFAULT 0`）、`is_locked`（`BOOLEAN NOT NULL DEFAULT false`）、`locked_at`（`TIMESTAMPTZ`）を追加する。`deleted_at` と同じく「日時列の `NULL` でフラグを兼ねる」形（`locked_at` のみ）も検討したが、**解除後も「最後にロックがかかった日時」を残す**という要件を満たせないため、フラグと日時を別の列とした。その結果、`is_locked` が `false` で `locked_at` に日時が入っている状態（過去にロックされたが解除済み）が正常な状態となる。2 つの列の整合は Go 側で担保する（`CHECK` 制約を置かない方針は本 ADR のとおり）。

**「取得系のクエリにはすべて `WHERE deleted_at IS NULL` が必要」は、もはや正しくない** — 管理者が削除済みユーザーを確認できるよう、一覧と 1 件取得は `?include_deleted=true` を指定したときに削除済みも含める仕様とした。この 2 つのエンドポイントでは条件が可変になる。第二段階のログイン照合で `WHERE deleted_at IS NULL` が必須である点は変わらない。

**`name` の `COLLATE "ja-JP-x-icu"` は当面使われない** — 一覧の並び順を `ORDER BY id`（登録順）としたためである。本 ADR に記したとおり漢字は読み順に並ばず、日本人名の一覧としては期待どおりの並びにならないため、誤解を招く並びを見せない判断をした。列に付いていること自体は無害で、将来カナの列を追加して名前順に並べる際にはそのまま効く。

**「同じメールアドレスでの再登録は既存の行を復帰させる」方針は、ステップ 1-4 では実装しない** — `POST` が「新規登録」と「復帰」の 2 つの意味を持つ複雑さが、テンプレートの目的に見合わないため。代わりに、衝突相手が生きているか削除済みかでエラーコードを分ける（`email_already_exists` / `email_belongs_to_deleted_user`、いずれも 409）。復帰を実装するまで、**一度使ったメールアドレスは、そのユーザーを削除した後も再利用できない**。

## 追記：ステップ 2-3 の仕様策定にともなう変更

ステップ 2-3（ログイン画面とマイページ）の仕様を固める過程で、本 ADR の内容に 1 点の追加が生じた。経緯は [0015-login-and-my-page-screens.md](0015-login-and-my-page-screens.md) に記録している。

**最終ログイン日時の列 `last_login_at`（`TIMESTAMPTZ`、NULL を許可）を `000005` で追加する** — ログインに成功したときに更新し、一度もログインしていないユーザーは `NULL` とする。`updated_at` は更新しない。
