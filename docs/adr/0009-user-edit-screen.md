# ユーザー編集画面の更新結果の反映と離脱確認

ステップ 1-5 のユーザー編集画面について、**更新の結果は一覧の 1 行だけを差し替えて反映し、離脱確認は「入力があるか」ではなく「元の値と異なるか」で判定し、変更がないときは通信せずアラートで知らせる**ことを決めた。画面の実装に着手する前に決めたのは、1 つ目が一覧画面の `UsersViewModel` と編集画面の戻り値の形を同時に決めてしまい、2 つ目が登録画面から引き継ぐつもりだった仕組みをそのままでは使えないことを意味するためである。

基本の動作・レイアウト・エラーの振り分けは、ユーザー登録画面（[0008-user-create-screen.md](0008-user-create-screen.md)）をそのまま踏襲する。以下は、踏襲**できなかった**点と、編集画面で新たに生じた点だけを記録している。

## 検討した選択肢

**更新結果の反映 — 一覧を再読み込みする（登録画面と同じ）** — 登録画面は `context.pop(true)` で「登録した」という真偽値だけを返し、一覧が `load()` で取り直している。編集でも同じ形にできるが、現在の `_load` は**成功・失敗のどちらでも選択を解除する**実装であり、「編集の後も行の選択を維持する」ためには `UsersViewModel` の側を変えることになる。そこで崩れるのは「一覧の中身が入れ替わったら選択を外す」という規則で、これは画面に見えていない行が選択されたままになるのを防ぐためのものだった。編集は 1 人のユーザーの名前とメールアドレスだけを変える操作であり、一覧の中身が入れ替わる操作ではない。

**更新結果の反映 — 一覧がそのユーザー 1 件を取り直す** — `GET /api/users/{id}` を呼んで差し替える案。結果は 1 行差し替えと同じだが、更新の直後にもう 1 往復の通信が入り、「取り直しに失敗したらどうするか」という失敗経路が新たに 1 つ増える。`PUT` が既に更新後のユーザーを返している以上（ADR 0004）、取りに行く必要がない。

**離脱確認 — 登録画面の `hasInput` をそのまま使う** — 登録画面は「4 つの入力欄のいずれかに文字があるか」で判定している。編集画面は取得した値が最初から入っているため、この基準では**常に真**になり、1 文字も触らずに「戻る」を押しただけで破棄の確認が出る。欄を空にしたときだけ確認が出ない、という逆の挙動になる。

**離脱確認 — 一度でも入力欄を編集したか（`onChanged` が走ったか）で判定する** — 実装は最も単純だが、打ち直して元の値に戻しても「編集途中」のままになる。利用者から見れば、画面上の値は元どおりなのに確認が出る理由が分からない。

**変更がないときの扱い — そのまま更新を実行する** — 何も変わっていない `PUT` を送り、200 が返って「更新が完了しました」と表示する案。サーバー側は正しく動作するが、利用者は「何を更新したのか」を確認する手立てがないまま完了を告げられる。

**「同じ」の判定 — 生の入力文字列を比較する** — 末尾に空白を足しただけでも「変更あり」となって `PUT` が走る。サーバー側で整形されるため保存結果は元と同じだが、利用者には「更新が完了しました」と表示される。

**「同じ」の判定 — 大文字小文字も無視する** — メールアドレスの小文字化は Go 側に一本化しているため（ADR 0002）、`user@example.com` を `User@example.com` に直しても保存結果は変わらない。ただしこれを「変更なし」とすると、**画面に見えている文字列と判定が食い違う**（打ち直したのに「編集されていません」と出る）。

**編集対象の示し方 — 何も足さない** — 入力欄の初期値がそのまま対象を示している、という考え方。しかしユーザー名欄を書き換えた時点で、どのユーザーを編集しているのかを示すものが画面から消える。タイトルは「ユーザー情報編集」で対象を含まない。

**編集対象の示し方 — ユーザー ID を表示する** — 値が変わらない点は良いが、**一覧のテーブルに ID 列がない**ため、一覧と突き合わせる手がかりにならない。

**URL — ID をパスに載せず `extra` で User を渡す** — URL に ID が出ないため、ブラウザで再読み込みすると対象を失う。開発中に特定のユーザーの編集画面を直接開くこともできない。

## 結果として生じること

- **`UsersViewModel` に `replaceUser` が加わり、アカウントロック解除もこれを通るようになる。** 「更新系は更新後のユーザーを返す」という ADR 0004 の規約を活かした 1 行差し替えは、これで 2 例目になる。一覧の並びは `ORDER BY id` のため、名前やメールアドレスが変わっても行の位置は動かない。
- **編集画面は一覧へ 3 通りの値を返す。** `null`（「戻る」で離脱した・取得に失敗した＝何もしない）、`UserEditResult.updated`（1 行差し替え）、`UserEditResult.reloadNeeded`（一覧を取り直す）の 3 つ。登録画面の真偽値 1 つでは足りない。
- **通信が切れたときと 404 のときだけ、行の選択が外れる。** どちらも手元の一覧が実態とずれていることが確定しており、一覧を取り直すためである。「戻る」・取得の失敗・更新の成功の 3 経路では選択もページも維持される。
- **`UserEditState` は取得したユーザーそのものを持つ。** 登録画面の `UserCreateState` は真偽値 2 つしか持たなかったが、編集画面は「編集前の値」の表示と「変更されていない」の判定の両方にこの値を必要とする。入力中の文字列を View（hooks）に置く方針は変わらない。
- **`GET /api/users/{id}` に `include_deleted` は付けない。** 削除済みのユーザーは更新系がすべて 404 を返すため（ADR 0004）、取得の時点で 404 になるのが正しい。編集できない画面を編集できる形で見せない。
- **アラートが出たかどうかで「入力の問題か、環境の問題か」を切り分けられる性質は保たれる。** 409 と 400 の内訳は入力欄の直下に出す（ADR 0008）。ただし「変更されていません」はこの切り分けの例外で、**入力の問題でありながらアラートに出る唯一のもの**になる。特定の欄に結び付かないためである。
- **編集画面の `_labelWidth` は 180px を登録画面と共有している。** この画面の最長ラベルは「メールアドレス」で余るが、片方だけ詰めると一覧 → 登録 → 一覧 → 編集と移動したときに入力欄の左端が画面ごとにずれる。
- **API がアラートの本文として返す日本語の文言に句点が付いた。** 404 の「ユーザーが見つかりません」の後ろに「OK を押すと〜」という別の文が続くため、句点がないと文が途切れて見える。同じ理由が当てはまる 7 件（`not_found` / `internal_error` / `invalid_id` / `invalid_json` / `validation_error` の総括文 / パスの fallback 2 件）をまとめて直した。**入力欄の直下に単独で出る 409 の 2 件と `fields` の 13 件は句点なしのまま**で、Dart 側に二重化されている検証の文言にも手を入れていない。
- **`/users/{id}/edit` を直接開ける。** go_router は子ルートへ直接来た場合も親（`/users`）を下に積むため、「戻る」は一覧へ行く。ただしその一覧は既定の状態（1 ページ目・削除済み非表示・選択なし）で開かれる。ID が整数でない URL（`/users/abc/edit`）は、成立していない URL として一覧へリダイレクトする（アラートは出さない）。
