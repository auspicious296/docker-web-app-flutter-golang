# ログイン・ログアウトの API の仕様

ステップ 2-2 の「ログイン・ログアウトの API を作成する」について、[ADR 0012](0012-session-based-authentication.md) と [ADR 0013](0013-session-timeouts-and-user-crud-access.md) で決めていなかった API の仕様を決めた。**ログインの失敗は、ロックだけを区別して返す。失敗の回数は、ログインと本人によるパスワード変更で共通に数え、パスワード変更で 5 回連続で誤ったら、ロックしたうえでそのセッションを削除する（強制ログアウト）。** nginx の呼び出し回数の制限はログイン API だけにかけ、正規の利用者が一斉にログインしても届かない値とする。自動テストは `repository` 層まで書き、テスト用 DB は開発環境の起動時に自動で作成する。

実装の前に決めたのは、レスポンスの形とエラーコードが Flutter 側（ステップ 2-3）の DTO・画面の処理に連鎖し、失敗の回数とロックの扱いがセキュリティの守りそのものであるためである。

## 決定した内容

### ログイン API（`POST /api/login`・`POST /api/mobile/login`）

**成功したとき**

| クライアント | ステータスコード | 本文 |
|---|---|---|
| Web（`POST /api/login`） | 204 | なし。セッション ID は Cookie で渡す（ADR 0012） |
| モバイル（`POST /api/mobile/login`） | 200 | `{"session_id":"..."}` |

- ユーザー情報は含めない。ユーザー情報は `GET /api/me` で受け取る
- CSRF トークンは含めない。ADR 0012 のとおり、`GET /api/csrf-token` でだけ受け取る
- ログインに成功したら、`failed_login_attempts` を 0 に戻す

**失敗したとき**

| 状況 | ステータスコード | エラーコード | メッセージ | `failed_login_attempts` |
|---|---|---|---|---|
| メールアドレスかパスワードが空 | 400 | `validation_error`（`fields` に `email` / `password`） | 入力内容に誤りがあります。（`fields`：「メールアドレスを入力してください」など） | 数えない |
| 登録済みのメールアドレスで、パスワードが誤っている | 401 | `invalid_credentials` | メールアドレスまたはパスワードが正しくありません。 | 1 加算する。5 に達したらロックし、403 `account_locked` を返す |
| メールアドレスが未登録（削除済みを含む） | 401 | `invalid_credentials` | メールアドレスまたはパスワードが正しくありません。 | 数えない（加算する対象のユーザーがいない） |
| ロック中 | 403 | `account_locked` | アカウントがロックされています。管理者に解除を依頼してください。 | 数えない（パスワードを照合しない） |

- **失敗の回数を数えるのは、「メールアドレスとパスワードの両方に値が入っていて、登録済みのメールアドレスで、パスワードが誤っていたとき」だけ**である
- ロック中は、パスワードを照合せず、すぐに 403 `account_locked` を返す
- メールアドレスが未登録のときも、ダミーのハッシュ値で bcrypt の照合を行い、応答時間を揃える
- メールアドレスは、小文字に変換してから照合する（[ADR 0002](0002-users-table-schema.md)）
- 入力の検証は「空かどうか」だけを行う。登録時の形式の規則（[ADR 0008](0008-user-create-screen.md) の「8 文字以上 72 文字以内、ASCII の印字可能文字のみ」など）は使わない
- **72 バイトを超えるパスワードは、照合に使わず「一致しない」として扱う。** パスワードは完全一致だけを許可する
- ログイン状態にある古いセッション（Cookie または `Authorization` ヘッダーで送られてきたもの）は、ログイン API が削除し、新しいセッションを発行する

### `GET /api/me`

- 200 と `{"id":1,"name":"山田 太郎","email":"taro@example.com"}` の 3 項目を返す。既存の 1 件取得と同じく、包まずにオブジェクトをそのまま返す

### `PUT /api/me/password`（本人によるパスワード変更）

リクエストの本文は `{"current_password":"...","new_password":"..."}` とする。確認用の入力欄の値は、[ADR 0010](0010-user-password-reset-screen.md) と同じく API に送らない。

| 状況 | ステータスコード | 返すもの | `failed_login_attempts` |
|---|---|---|---|
| 成功 | 204 | なし | 0 に戻す |
| 現在のパスワードが空 | 400 | `validation_error`（`fields` の `current_password` に「入力してください」） | 数えない（照合しない） |
| 現在のパスワードの誤り（1〜4 回目） | 400 | `validation_error`（`fields` の `current_password` に「現在のパスワードが正しくありません」） | 1 加算する |
| 現在のパスワードの誤り（5 回目） | 403 | `account_locked` | 5 になり、ロックする。**失敗させたそのセッションを削除する** |
| ロック中 | 403 | `account_locked` | 数えない（照合しない） |
| 新しいパスワードが現在のパスワードと同じ | 400 | `validation_error`（`fields` の `new_password` に「現在のパスワードと同じパスワードは設定できません」） | 0 に戻す（照合に成功しているため） |

- 新しいパスワードは、登録時と同じ規則（ADR 0008）で検証する
- **新しいパスワードの形式の検証と、現在のパスワードの照合は両方行い、誤りを `fields` にまとめて返す。** 新しいパスワードの形式が誤っていても、現在のパスワードの誤りは数える
- 72 バイトを超える現在のパスワードは、ログイン API と同じく「一致しない」として扱う
- 成功したら、変更した端末以外のセッションを削除する（ADR 0012）

**ロックのきっかけによって、セッションの扱いが異なる**

| ロックのきっかけ | 失敗させた者 | セッションの扱い |
|---|---|---|
| ログインの失敗 | セッションを持たない外部の者 | 削除しない（ADR 0012） |
| パスワード変更での、現在のパスワードの誤り | そのセッションの持ち主 | 失敗させたそのセッションを削除する。ほかの端末のセッションは削除しない |

### `POST /api/logout`

- 成功したら 204（本文なし）を返し、セッションの行を削除する。Web では、有効期限切れの Cookie を送って Cookie を消させる
- セッションがない、またはログイン状態にない場合は、ほかのログインが必要な API と同じく、ミドルウェアが 401 `unauthenticated` を返す。ログアウトの API を例外にしない

### ミドルウェアが拒否するときのエラーコード

| ミドルウェアが拒否する場合 | ステータスコード | エラーコード | メッセージ |
|---|---|---|---|
| 送られてきたセッションがない、またはログイン状態にない | 401 | `unauthenticated` | ログイン状態ではありません。ログインしてください。 |
| `Origin` が許可したオリジンではない（ない場合を含む） | 403 | `origin_not_allowed` | 許可されていない送信元からのリクエストです。 |
| CSRF トークンがない、または一致しない | 403 | `csrf_token_invalid` | リクエストを検証できませんでした。画面を再読み込みしてください。 |
| セッション ID が Cookie とヘッダーの両方で送られてきた | 400 | `ambiguous_session` | セッション ID が Cookie とヘッダーの両方で送られています。 |

### 許可するオリジン（`ALLOWED_ORIGIN`）

| 環境 | 値を書く場所 | 値 | 起動のコマンド |
|---|---|---|---|
| 開発環境 | `compose.yaml` の `api` の `environment` | `https://myapp.local` | `docker compose up -d` |
| 本番環境 | `compose.prod.yaml` の `api` の `environment` | 本番のドメイン | `docker compose -f compose.yaml -f compose.prod.yaml up -d` |

- どちらのファイルも書き換えず、起動のコマンドで読ませるファイルを変えて切り替える。Docker Compose は、後に指定した `compose.prod.yaml` の値で `compose.yaml` の値を上書きする
- 値が設定されていなければ、API は起動時に中止する（保持期間の値・`CSRF_SIGNING_KEY` と同じ扱い）
- `compose.prod.yaml` は、本番のデプロイの方法を決める時点で作成する。本ステップで作成するのは、`compose.yaml` への記載だけである

### nginx の呼び出し回数の制限

| 項目 | 内容 |
|---|---|
| 対象 | `POST /api/login` と `POST /api/mobile/login`。2 つを合わせて数える |
| 数え方 | 同じ送信元（IP アドレス）からの呼び出しを、成功・失敗を問わずすべて数える |
| 平均の上限 | 1 秒に 1 回（1 分間に 60 回） |
| 一時的な超過の許容（`burst`） | 60 回 |
| 超過したとき | nginx が 429 と `{"error":{"code":"too_many_requests","message":"ただいまログインの処理が集中しているため、受け付けられませんでした。\nしばらく待ってから、もう一度お試しください。"}}` を返す |

- **`GET /api/csrf-token` は対象外とする。** ADR 0012 の決定を変更した（理由は「検討した選択肢」のとおり）
- 制限にかかったリクエストは Go の API まで届かないため、パスワードの照合も `failed_login_attempts` の加算も行われない
- nginx は何も設定しなければ 503 と HTML のエラーページを返すため、429 と上記の JSON を返すように設定する
- この値は雛形の値である。本番では、同じ IP アドレスから同時にログインする利用者の実際の人数に合わせて調整する

### 第一段階の API へのセッション削除の追加

- ADR 0012 で決めた「管理者がユーザーを削除する／パスワードをリセットすると、そのユーザーの全セッションを削除する」処理は、本ステップ（2-2）で、`DELETE /api/users/{id}` と `PUT /api/users/{id}/password` に追加する

### 自動テストとテスト用 DB

- 自動テストは、`service` 層・`handler` 層・ミドルウェアに加えて、**`repository` 層まで書く**。`repository` 層のテストはテスト用 DB を使う
- テスト用 DB は、今の PostgreSQL のコンテナの中に、開発用 DB とは別のデータベースとして作る
- テスト用 DB の作成は、開発環境専用のファイル `compose.override.yaml` に、PostgreSQL の起動後に 1 回だけ動いて終わるサービスとして書く。この処理は、テスト用 DB がなければ作成し、すでにあれば何もしない

| 環境 | 起動のコマンド | テスト用 DB の作成 |
|---|---|---|
| 開発環境 | `docker compose up -d` | 自動で実行される |
| 本番環境 | `docker compose -f compose.yaml -f compose.prod.yaml up -d` | 実行されない |

- Docker Compose は、`-f` の指定がないときだけ `compose.override.yaml` を自動で読む。本番のコマンドは `-f` を指定するため、`compose.override.yaml` を読まない
- テストは、実行を始めるときにテスト用 DB のテーブルを空にする。テスト用 DB は残しておく前提であり、後片付けは不要である

## 検討した選択肢

**ログインの失敗 — すべて同じエラーで返す** — レスポンスから、メールアドレスが登録されているかを知る手段がなくなる。しかし、ロックされた本人はロックに気付けず、正しいパスワードを入れても「正しくありません」と表示され続け、管理者に解除を頼めない。ステップ 1-5 のパスワードリセット画面で、ロック中であることを赤字で表示した配慮（ADR 0010）とも矛盾する。本プロジェクトにはサインアップがなく、アカウントの列挙で攻撃者が得られるものは少ない。ロック専用のエラーで登録を知るには 5 回失敗させる必要があり、その時点で相手はロックされる。

**ログインの失敗 — パスワードが正しいときだけロックを明かす** — 列挙を防ぎつつ本人には伝わるように見える。しかし、ロック中も「正しいパスワードかどうか」を試し続けられることになり、ロックが総当たりへの守りとして働かなくなる。

**ロックのステータスコード — 423 / 401** — 423 は「対象がロックされている」を表すが、本来は WebDAV のためのステータスコードで、一般の API ではなじみが薄い。401 は「正しい認証情報を送り直せば通る」を表し、正しいパスワードでも通らないロックの意味と食い違う。403 は `Origin`・CSRF トークンの拒否と同じステータスコードになるが、Flutter はエラーコードで処理を分けるため支障はない。同じステータスコードをエラーコードで分ける形は、登録時の 409（`email_already_exists` / `email_belongs_to_deleted_user`）に前例がある。

**ロック中のログイン — パスワードを照合し、誤りなら加算し続ける** — 増えた回数はロック解除で 0 に戻るため、使い道がない。照合（bcrypt）を省けば、ロック中のアカウントを狙った大量の呼び出しで API に負荷をかけられにくくなる。

**未登録のメールアドレス — 応答時間を揃えない** — 未登録なら DB を引くだけで速く返り、パスワードの誤りなら bcrypt の分だけ遅く返る。この差を測れば、本文を見なくても、ロックさせずに気付かれずにメールアドレスの登録を調べられる。OWASP の Authentication Cheat Sheet も応答時間を揃えることを勧めている。

**ログイン API のレスポンスにユーザー情報を含める** — ログインの直後の呼び出しが 1 回減る。しかし、Web は画面の再読み込みや URL の直接入力で、モバイルはアプリの起動し直しで、ログイン API を通らずに使い始めるため、どのみち `GET /api/me` を呼ぶ必要がある。ユーザー情報を取る経路を `GET /api/me` の 1 本にまとめ、同じ形を 2 か所で保守することを避けた。Web はログインの直後に `GET /api/csrf-token` を呼ぶことがすでに決まっており（ADR 0012）、ログインの後に続けて API を呼ぶ流れは元からある。

**`GET /api/me` — 管理者向けの 9 項目をそのまま返す** — 既存の処理をそのまま使える。しかし、ログインできている本人にとって `deleted_at`（常に `null`）・`is_locked`（常に `false`）・`failed_login_attempts`（常に `0`）は意味がなく、`locked_at` は管理者が確認するための記録である。

**パスワード変更の誤り — 数えない** — 現在のパスワードを照合する目的は、ログインしたまま放置された PC などで、本人以外がパスワードを変えられないようにすることである。数えなければ、その者は現在のパスワードを何度でも試せる。nginx の呼び出し回数の制限はログイン API にしかかけない。NIST SP 800-63B は、アカウントに対する認証の失敗回数を制限することを求めており、ログインか再確認かを区別していない。

**パスワード変更の誤り — ログインとは別に、そのセッションの中だけで数える** — 本人の打ち間違いでもロックされない。しかし、アカウント単位の制限にならず、セッションの行に失敗回数の列を足してロックとは別の仕組みを作ることになる。

**パスワード変更でロックしても、セッションを削除しない** — ADR 0012 の「ロックではセッションを削除しない」をそのまま当てはめる案。しかし ADR 0012 がセッションを削除しないとしたのは、ログインの失敗が、セッションを持たない外部の者によって起こされるためである（削除する扱いにすると、他人が本人を強制ログアウトさせられる）。パスワード変更での失敗は、セッションを持っている者自身が起こしており、疑わしいのはまさにそのセッションである。本人確認に続けて失敗したセッションは乗っ取りを疑うべきであり、破棄するのがセッション管理の原則である。残せば、疑わしい者がログインしたまま操作を続けられ、ロックをかける意味と矛盾する。

**現在のパスワードの誤り — 401 `invalid_credentials`** — 401 は「ログイン状態にない」（ADR 0012）の意味と重なる。アプリが 401 を受けたらログイン画面へ移す作りにすると、打ち間違えただけでログイン画面へ飛ばされる。

**現在のパスワードの誤り — 403 `current_password_incorrect`** — 専用のエラーコードで区別できるが、入力欄への結び付けを画面側で個別に書く必要がある。現在のパスワードの誤りは「入力欄に入れた値が誤っている」ものであり、形式の誤りと同じく、既存の `fields` の仕組み（ADR 0008）にそのまま乗せられる。

**新しいパスワードの形式を先に検証し、誤りならそこで止める** — 現在のパスワードの誤りは、新しいパスワードを直して送り直した後に初めて分かり、送信が 2 回必要になる場合がある。既存の検証も「1 つ目の不正で打ち切らず、不正な項目をすべて返す」作りである。

**パスワード変更の成功 — 200 と `GET /api/me` と同じ 3 項目を返す** — パスワードを変更しても id・名前・メールアドレスは変わらず、返す内容は画面がすでに持っている値と同じである。ADR 0004 の「更新系はすべて更新後のユーザーを返す」は、管理者向けのユーザー API についての規則とした。

**新しいパスワードが現在のパスワードと同じでも受け付ける** — 利用者はパスワードを変えるつもりで操作している。同じパスワードを入れてしまったのに成功と返すと、変わっていないことに利用者が気付けない。

**セッションが切れた状態でのログアウト — 204 を返す** — 「ログアウトした状態にする」という結果だけを見れば、何度呼んでも同じ結果になる。しかし、ログアウトの API だけをミドルウェアの規則（セッションがない・無効なら 401）の例外にする必要があり、セッションがないため CSRF トークンの照合ができず、判定を飛ばす経路が 1 本できる。どちらの案でも、アプリはログアウトした状態としてログイン画面へ移る。

**ログイン状態にある古いセッション — 残す / ログインを拒否する** — 残すと、Cookie は新しいセッションで上書きされるため、古いセッションは誰にも使われないまま DB に最長 8 時間残る。ログインを拒否すると、ログイン状態にあるセッションとタイムアウトで切れたセッションを区別する処理がログイン API に必要になり、利用者は先にログアウトしないと別のユーザーでログインできない。OWASP の Session Management Cheat Sheet は、ログインのときにそれまでのセッションを無効にして新しいセッションを発行するよう勧めている。

**`Origin` の拒否と CSRF トークンの拒否を 1 つのエラーコードにまとめる** — 攻撃者に、どちらの判定で拒否されたかを知らせずに済む。しかし、どちらの判定も「正しいブラウザから、正しい手順で送る」ことしか求めておらず、知られても突破の助けにはならない。分けておけば、開発者が `curl` で API を試したときに、`Origin` ヘッダーの付け忘れか CSRF トークンの付け忘れかを本文から見分けられる。

**許可するオリジン — `.env` / コードに書く** — `.env` は Git で管理されず、開発者ごとに値が食い違っても気付けない（ADR 0013 が保持期間の値を `.env` に置かなかった理由と同じ）。コードに書くと、本番のドメインに変えるたびにコードの修正とビルドが必要になる。

**呼び出し回数の制限 — 1 分間に 10 回、一時的な超過の許容 5 回** — 1 人の利用者だけを考えれば十分な値に見える。しかし nginx は、同じ IP アドレスを共有する利用者（同じオフィスなど）の呼び出しを、成功・失敗を問わず合わせて数える。始業時刻に一斉にログインすると、正しいメールアドレスとパスワードを入れた利用者が、他人の呼び出しのあおりで拒否される。送信元ごとの制限は、正規の利用者が一斉にログインしても届かない高さに設定し、1 つの送信元から大量に送りつける攻撃だけを止めるのが本来の使い方である。1 つのアカウントへの総当たりは、アカウントロックが止める。

**呼び出し回数の制限 — `GET /api/csrf-token` にもかける（ADR 0012 の当初の決定）** — `GET /api/csrf-token` は DB に書き込まず、署名の計算だけで終わり、`/api/health` と同程度に軽い。ADR 0012 でも、制限が「欠かせない」理由として挙げていたのは、ログイン API が bcrypt を実行する重い処理であることだった。ログイン API は、呼ばれるたびに bcrypt を実行し（未登録のメールアドレスでも実行する）、制限がなければ 1 つの送信元から大量に呼ぶだけで API サーバーの CPU を使い切れる。

**第一段階の API へのセッション削除 — 後のステップで行う** — 行わない期間は、管理者がユーザーを削除してもそのユーザーのセッションが残り、タイムアウトまでログイン状態が続く。セッションを削除する処理は、セッションのテーブルができて初めて書け、そのテーブルは本ステップで作成する。

**自動テスト — `service` 層と `handler`・ミドルウェアだけにする** — テスト用 DB がいらない。しかし、ADR 0013 のとおりタイムアウトの判定は SQL（`UPDATE ... RETURNING`）の中に書かれるため、タイムアウトの判定・期限切れのセッションの定期削除・失敗回数の加算とロック・セッションの削除が自動テストで確かめられず、ADR 0012 の「決定を 1 項目ずつ自動テストで確かめる」を満たせない。

**テスト用 DB — テスト専用の PostgreSQL のコンテナを追加する / `testcontainers-go` でテストのたびに起動する** — 前者はコンテナが 1 つ増える。後者は外部のライブラリが増え、[ADR 0003](0003-backend-database-access-and-routing.md) の「外部依存を `pgx` と `golang.org/x/crypto` の 2 つに限定する」が崩れる。

**テスト用 DB の作り方 — 各開発者が手元で作成のコマンドを実行する / PostgreSQL の初期化スクリプト / マイグレーション** — 手作業のコマンドは、手順が 1 つ増える。PostgreSQL の初期化スクリプトは、データを保存しているボリュームが空のとき（最初の 1 回）にしか動かず、すでに開発環境を作っている開発者の手元では動かない。また、`compose.yaml` に設定すると本番でも動く。マイグレーションは本番でも適用するため、本番にもテスト用 DB が作られる。

**ログイン API で、登録時と同じ形式の検証を行う** — 形式の誤りを 400 で知らせられる。しかし ADR 0008 のとおり、ログインを実装した後に登録時の規則を狭めると、古い規則で登録したユーザーが、ログイン API の形式の検証で弾かれてログインできなくなる。

**72 バイトを超えるパスワード — 何もしない** — bcrypt はパスワードの先頭 72 バイトしか使わず、Go の `bcrypt.CompareHashAndPassword` は 72 バイトを超えるパスワードを拒否せずに先頭 72 バイトだけで照合する。何もしなければ、72 文字のパスワードを登録したユーザーは、その後ろに余計な文字を付けて入力してもログインできてしまう。72 バイトは登録時の規則ではなく bcrypt の技術的な上限であり変わらないため、「一致しない」と扱っても、正規のユーザーがログインできなくなることはない。形式の検証をしないという決定とも矛盾しない。

## 結果として生じること

- **ADR 0012 の「ログイン前に呼べる API（`GET /api/csrf-token`、両方のログイン API）に nginx で呼び出し回数の制限をかける」は、もはや正しくない。** 制限をかけるのはログイン API の 2 つだけである。
- **ADR 0004 の「更新系はすべて更新後のユーザーを返す」は、管理者向けのユーザー API だけの規則となる。** `PUT /api/me/password` は 204 を返す。
- **Flutter 側は、204 を成功として扱う対応が必要になる。** Web のログイン・ログアウト・パスワード変更が 204 を返す。ADR 0008 のとおり、既存の `UserApiClient._decode` は 200 だけを成功とみなしている。
- **本人が現在のパスワードを 5 回連続で打ち間違えると、ロックされて強制ログアウトになり、管理者に解除を依頼するまでログインできない。**
- **ログインでロックされた場合、ログイン中の端末のセッションは残るが、パスワード変更は照合されずに 403 `account_locked` になる。** マイページの表示とログアウトはできる。
- **nginx のアクセスログの上では、ロックと `Origin`・CSRF トークンの拒否は、どれも 403 として並び区別できない。** 区別が必要になった場合は、Go の API 側のログにエラーコードを出す。
- **送信元の IP アドレスごとの制限は、多数の送信元に分散した攻撃は止められない。** これは値の問題ではなく、この仕組みの限界である。
- **nginx の設定に、429 と JSON を返す設定が必要になる。** 既定の 503 と HTML のままでは、ADR 0004 の「`/api/` 配下の失敗は必ず `{"error":{...}}` の形で返す」が崩れる。
- **本番で `-f` を付けずに `docker compose up -d` を実行すると、`compose.override.yaml` が読まれ、本番にもテスト用 DB が作られる。** 本番では必ず `-f` で `compose.yaml` と `compose.prod.yaml` の 2 つを指定する。
- **開発ガイド（[development-guide.md](../development-guide.md)）の更新が必要になる。**
  - デプロイの節を追加し、`ALLOWED_ORIGIN` の置き場所（開発は `compose.yaml`、本番は `compose.prod.yaml`）、環境ごとの起動コマンド、本番では必ず `-f` で 2 つのファイルを指定することを記載する
  - 「3. バックエンド（Go） > 開発中の確認方法」で、ホストから `go run ./cmd/api` を実行するときに `export` する環境変数に、`ALLOWED_ORIGIN`・保持期間の 4 つの値・`CSRF_SIGNING_KEY` を加える。いずれも未設定なら API が起動時に中止するためである
  - 「1. 開発の進め方の概要」に、`docker compose up -d` でテスト用 DB も自動で作成されることを記載する
  - 「3. バックエンド（Go） > 開発中の確認方法」のテストの実行方法に、`repository` 層のテストはテスト用 DB を使うため、先に `docker compose up -d` で起動しておく必要があることを記載する

## 追記：実装プランの策定にともなう決定

実装プランを立てる過程で、次の事項を決めた。

**テスト用 DB へのマイグレーションの適用** — 開発環境の `docker compose up -d` のとき、`compose.override.yaml` の処理が、テスト用 DB の作成に続けて、migrate の公式イメージ（`migrate/migrate:v4.20.1`）でマイグレーションを適用する。適用済みのマイグレーションは飛ばすため、何度実行してもよい。新しいマイグレーションを追加したときは、`docker compose up -d` を実行し直すまでテスト用 DB には反映されない。テストのコードで `backend/migrations/` の SQL を実行する案は、migrate の仕組み（どこまで適用したかの記録など）を自前で真似ることになるため採らなかった。開発者が手動で適用する案は、適用し忘れが起こり得るため採らなかった。

**テスト用 DB に接続できないときの `repository` 層のテスト** — 飛ばさずに失敗させ、「先に `docker compose up -d` を実行してください」と表示する。飛ばすと、タイムアウトの判定やロックなど、ADR 0012 で「自動テストで確かめる」と決めた処理が、確かめられないまま「成功」と表示され得るためである。接続先は環境変数 `TEST_DATABASE_URL` で受け取る。

**実装上の細目**

| 細目 | 決定 |
|---|---|
| 保持期間の環境変数の名前 | `SESSION_WEB_IDLE_TIMEOUT`・`SESSION_WEB_ABSOLUTE_TIMEOUT`・`SESSION_MOBILE_IDLE_TIMEOUT`・`SESSION_MOBILE_ABSOLUTE_TIMEOUT` |
| ログイン前の CSRF トークンの Cookie | 名前は `__Host-csrf`。値は「トークン.署名」。ログインに成功したら削除する（ADR 0012 の「引き継がない」） |
| セッション ID・CSRF トークンの文字列 | 32 バイトの乱数を base64url（パディングなし、43 文字）にする |
| `GET /api/csrf-token` のレスポンス | 200 `{"csrf_token":"..."}`。`Cache-Control: no-store` を付ける |
| ログインのメールアドレス | 登録時と同じく、前後の空白を除いて小文字にしてから照合する |
| 失敗の回数の加算・0 に戻すときの `updated_at` | 更新しない（利用者の情報の変更ではないため）。ロックしたときだけ更新する（ロック解除が更新しているのとそろえる） |
| 72 バイトを超えるパスワード | ダミーのハッシュ値で bcrypt を実行して応答時間を揃えたうえで、失敗として扱う |
| テスト用 DB の名前 | `<POSTGRES_DB>_test` |
| パスワードの更新・ユーザーの削除と、セッションの削除 | 1 つの SQL で同時に行う。パスワードだけが変わって古いセッションが残る、削除したユーザーがログイン状態のまま残る、という状態を作らないため |
| ミドルウェアの判定の順序 | 「Cookie とヘッダーの両方 → `Origin` → セッション → CSRF トークン」。罠サイトからのリクエストを、セッションの確認（最後の操作日時の更新）より前に弾くため |
