# ユーザー管理 API の設計

ステップ 1-4 で作る 7 本のエンドポイントについて、**エラーは `{"error":{"code","message","fields"}}` の形に統一し、削除済みユーザーは取得系でのみ `include_deleted` により明示的に含め、更新系はすべて更新後のユーザーを 200 で返す**ことを決めた。画面（ステップ 1-5）に着手する前に決めたのは、レスポンスの外形が Flutter 側の DTO・Repository・ViewModel に連鎖し、後から変えると API と画面の両方を直すことになるためである。

前提として、第一段階は「**管理者向けのユーザー管理画面を、認証部分を外して実験用に抜き出したもの**」と位置付ける。操作の主体は管理者であり、画面に並ぶユーザーは管理される側である。この位置付けは [develop-roadmap.md](../develop-roadmap.md) に記載しており、以下の判断の多くがここから導かれている。

## 検討した選択肢

**エラー表現 — `{"message":"..."}` のみ** — 最小の形だが、ステップ 1-5 の登録・編集画面は `name` / `email` / `password` を入力するフォームであり、項目ごとにエラーを表示できる必要がある。後から項目別の内訳（`fields`）を足すと API と画面の両方を直すことになるため、最初から持たせる。機械判別用の `code` を併せ持たせたのは、ステップ 1-2 の疎通確認画面が失敗の内訳を出し分けている方針と揃えるためである。

**エラー表現 — RFC 9457（Problem Details for HTTP APIs）** — HTTP API のエラー表現の標準仕様であり、拡張メンバで項目別の内訳も表せる。ただし `type` にエラー種別を識別する URI を置く設計で、ローカル完結の学習用アプリでは URI を決める手間に見合わない。Flutter 側も `application/problem+json` を解釈する DTO を別途持つことになる。

**削除済みユーザーの扱い — 取得系からも一律に隠す** — ADR 0002 が「取得系のクエリにはすべて `WHERE deleted_at IS NULL` が必要」としていた当初の方針。しかしこれを貫くと、**管理者が削除済みユーザーを確認する手段が画面上に存在しなくなる**。とくに、メールアドレスが削除済みユーザーと衝突したことを 409 で知らされても、その相手を確認できない。論理削除を選んだ意味（ADR 0002）は、管理画面から見えて初めて活きる。

**削除済みユーザーの扱い — 一覧で常に全件返し、画面側で絞り込む** — API に分岐が不要になる代わりに、`GET /api/users` を素朴に呼んだ側に削除済みが必ず混ざる。既定を安全側に倒すため、`include_deleted=true` を明示したときだけ含める形とした。`GET /api/users/{id}` にも同じパラメータを適用し、削除済みの扱いに関する規約を 1 つに揃えている。

**削除済みユーザーへの更新系 — `include_deleted` で許可する** — 取得系と同じ規約を更新系にも適用する案。採らなかったのは、**削除済みの行は「削除された時点の記録」であり、後から書き換えられるべきではない**ためである。削除済みユーザーの名前やパスワードを変更できることは、その記録を改ざんできる経路を作ることを意味する。将来「削除の取り消し」を実装する場合も、必要になるのは削除済みの行を対象とする専用のエンドポイント 1 本であり、既存の更新系を削除済みに開放する必要はない。

**削除済みユーザーと同じメールアドレスでの登録 — ADR 0002 が示す「復帰」** — ADR 0002 は「`deleted_at` を `NULL` に戻して既存の行を復帰させる」方針を記していたが、ステップ 1-4 では実装しない。テンプレートとしては `POST` が「新規登録」と「復帰」の 2 つの意味を持つ複雑さに見合わないためである。代わりに、**衝突相手が生きているか削除済みかでエラーコードを分ける**。管理者が「なぜ登録できないのか」を切り分けられるようにするためであり、ステータスはどちらも 409 で揃える。

**更新系のレスポンス — 204（本文なし）を返す** — `DELETE` に 204 を返すのは REST API の慣習として最も一般的である。ただしその場合「どのエンドポイントが 200 でどれが 204 か」をエンドポイントごとに覚えることになる。**「更新系はすべて更新後のユーザーを返す」という 1 行の規則**を優先した。Flutter 側は返ってきた値で画面の状態を差し替えられ、再取得が不要になる。`DELETE` が `deleted_at` 入りのユーザーを返すことは、一覧で「削除済みも表示」がオンのときにその行をそのまま差し替えられるという利点もある。

**一覧レスポンス — 裸の配列 `[{user}, ...]`** — ページングを入れないなら包む必然性はない。しかし後からページングを入れる際、JSON のトップレベルが配列からオブジェクトに変わる破壊的変更となり、Flutter 側の API クライアント・Repository・ViewModel の型が連鎖して変わる。最初から `{"users":[...]}` で包んでおけば、`page` / `per_page` / `total` の追加は後方互換な変更で済む。

**並び順 — `ORDER BY name`** — ADR 0002 で `name` に `COLLATE "ja-JP-x-icu"` を明示した狙いは、一覧を日本語として自然な名前順に並べることだった。しかし**漢字は読み順に並ばない**（ICU でも同じ）ため、日本人名の一覧としては期待どおりの並びにならない。誤解を招く並びを見せるより、`ORDER BY id`（登録順）とする。

**層の責務 — `service` が `code` や日本語メッセージまで持つ** — `handler` の変換処理（`switch`）が不要になる代わりに、`service` の中に HTTP と画面向けの文言が混ざる。層を分けた意味が薄れ、`service` のテストが文言の一致確認を含むようになるため、**`service` は「何が起きたか」だけを返し、HTTP ステータス・`code`・日本語メッセージは `handler` が持つ**形とした。

## 結果として生じること

- **ADR 0002 の「取得系のクエリにはすべて `WHERE deleted_at IS NULL` が必要」は、もはや正しくない。** 一覧と 1 件取得は `include_deleted` により条件が変わる。第二段階のログイン照合で `WHERE deleted_at IS NULL` が必須である点は変わらない。
- **ADR 0002 で `name` に付けた `COLLATE "ja-JP-x-icu"` は、当面使われない。** 列に付いていること自体は無害で、将来カナの列を追加して名前順に並べる際にはそのまま効く。
- **一度登録したメールアドレスは、そのユーザーを削除した後も再利用できない。** `UNIQUE` 制約が削除済みの行にも効いているためで、`email_belongs_to_deleted_user`（409）が返る。復帰を実装するまでこの状態が続く。
- **削除済みユーザーに対する更新系はすべて 404 を返す。** 画面側では、削除済みの行を選択したときに「編集」「パスワードリセット」「削除」「アカウントロック解除」をすべてディスエイブルドにすることで、404 に当たること自体を防ぐ。行の選択自体は可能とし、削除済みユーザーの内容を確認できる状態は保つ（論理削除を選んだ意味は、管理画面から見えて初めて活きるためである）。
- **`handler` にエラー変換の分岐が集中する。** エンドポイントごとに書くと重複するため、変換は 1 ファイル（`handler/errors.go` 相当）にまとめる。
- **Flutter 側は、失敗時に必ず `{"error":{...}}` が返るという前提で書ける。** `ServeMux` が既定で返す 404 / 405 もラッパーで JSON に揃えるため、`/api/` 配下に例外がない。
- **`page` / `per_page` に不正な値を送ると 400 になる**（黙って既定値へ丸めない）。範囲外のページ（`total` を超える `page`）は、空の配列を伴う 200 とする。データの増減でページ範囲が変わるのは異常ではないためである。
- **`failed_login_attempts` は第一段階では常に `0` を返す。** ログイン機能が存在しないためだが、レスポンスに含めておくことで第二段階に入っても形が変わらない。

## 追記：ステップ 1-5（ユーザー登録画面）の仕様策定にともなう変更

ユーザー登録画面の仕様を固める過程で、本 ADR の内容に 3 点の変更・補足が生じた。経緯は [0008-user-create-screen.md](0008-user-create-screen.md) に記録している。

**`fields` と `code` は、登録画面から実際に使われる** — 本 ADR は「ステップ 1-5 の登録・編集画面は項目ごとにエラーを表示できる必要がある」という予測に基づいて `fields` を設計したが、一覧画面（ステップ 1-5 の前半）では使う場面がなく、Flutter 側の `ApiErrorDto` は `message` だけを読んでいた。登録画面では **400 の `fields` を各入力欄の直下に表示し、409 の `code`（`email_already_exists` / `email_belongs_to_deleted_user`）を見てメールアドレス欄に結び付ける**ため、両方を画面まで運ぶ形に変わる。`fields` の `field` は enum に変換して扱い、**変換できない `field` が返った場合はアラートダイアログへ回す**。捨てるとエラーが 1 つも表示されないまま登録できない状態になり得るためである。

**パスワードの検証仕様が変わる** — 「8 文字以上、72 バイト以内、文字種の制限なし」から「**8 文字以上 72 文字以内、ASCII の印字可能文字（スペースを除く）のみ**」へ変更する。`POST /api/users` と `PUT /api/users/{id}/password` の両方に同時に効く。理由は ADR 0008 を参照。

**「画面側でディスエイブルドにして 404 を防ぐ」対象に、一覧の「新規登録」が加わる** — 本 ADR は削除済みユーザーに対する更新系について記していたが、登録画面ではこれと別に、**一覧の取得に失敗している間は「新規登録」も押せない**こととした。登録画面から戻った際に一覧を再読み込みする仕様のため、取得に失敗している状態から登録すると、登録は成功したのに一覧が空のままという状態を見せることになるからである。

## 追記：ステップ 2-3（ログイン画面とマイページ）の仕様策定にともなう変更

ステップ 2-3 の仕様を固める過程で、本 ADR の内容に 1 点の追加が生じた。経緯は [0015-login-and-my-page-screens.md](0015-login-and-my-page-screens.md) に記録している。

**ユーザー API のレスポンスに `last_login_at`（最終ログイン日時）を追加する** — 一覧・1 件取得・更新系のすべてのレスポンスに含める。一度もログインしていないユーザーは `null` である。管理者がユーザー一覧で確認するためのもので、`GET /api/me` には含めない。
