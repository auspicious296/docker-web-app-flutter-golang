# 認証方式（セッション方式）と、Web・モバイル共通のログインの仕組み

ステップ 2-1 の「認証方式を決定する」について、**ログイン状態はサーバー側のセッション（PostgreSQL）で管理し、セッション ID は Web アプリには HttpOnly の Cookie で、モバイルアプリには `Authorization` ヘッダーで送らせる**ことを決めた。CSRF 対策は、**CSRF トークンを基本の対策とし、`Origin` の判定を補強として重ねる**。仕組みはすべて Go の標準ライブラリで自前で作る。

ログイン・ログアウトの API（ステップ 2-2）に着手する前に決めたのは、認証方式が API の入り口の処理（ミドルウェア）、セッションのテーブル、Cookie の扱い、Web アプリの起動時の処理にまで連鎖し、後から変えるとそのすべてを作り直すことになるためである。

前提として、本プロジェクトはテンプレートだが、**本番プロジェクトでは Web アプリとモバイルアプリが同じ API を共通で使うことが確定している**。以下の判断の多くは、この前提を雛形の段階で先に形にしておくために下している。

ロードマップのステップ 2-1 のうち「ログイン状態の保持期間（アイドルタイムアウト・絶対タイムアウト）」と「ユーザー CRUD をログインしたユーザーのみに制限するか」は、本 ADR の対象外であり、別途決める（[ADR 0013](0013-session-timeouts-and-user-crud-access.md) で決定した）。

## 決定した内容

### セッション ID の送り方とログイン API

| クライアント | セッション ID の送り方 | ログイン API | セッション ID の返し方 |
|---|---|---|---|
| Web アプリ | HttpOnly の Cookie | `POST /api/login` | Cookie だけ。**レスポンスの本文には決して含めない** |
| モバイルアプリ | `Authorization: Bearer <セッション ID>` | `POST /api/mobile/login` | レスポンスの本文 |

- パスを分けるのはログイン API だけで、その他の API は Web とモバイルで同じパスを使う。ミドルウェアが Cookie かヘッダーのどちらかからセッション ID を読み取る
- **Cookie とヘッダーの両方にセッション ID が付いていたら 400 で拒否する**
- セッション ID がない、または無効なセッションで、ログインが必要な API を呼んだ場合は 401 を返す
- パスワードの照合とアカウントロックの処理は 1 か所にまとめ、両方のログイン API から呼び出す

### `Origin` の判定と CSRF 対策

| API | Web（Cookie） | モバイル（ヘッダー） |
|---|---|---|
| `POST /api/login`（Web 用のログイン） | ログイン前の CSRF トークン ＋ `Origin` の判定 | 使わない。`Origin` がないため 403 になる |
| `POST /api/mobile/login`（モバイル用のログイン） | 使わない。`Origin` があるため 403 になる | なし |
| `GET /api/csrf-token`（CSRF トークンの発行） | なし | 使わない |
| ログイン後の、データを変更する API（`POST` / `PUT` / `DELETE`） | CSRF トークン ＋ `Origin` の判定 | なし |
| ログイン後の、データを取得する API（`GET`） | なし | なし |

- **`Origin` の判定**：Web 用の API では、`Origin` が許可したオリジン（開発環境では `https://myapp.local`）でなければ、ヘッダーがない場合を含めて 403 を返す。モバイル用のログイン API では、`Origin` が付いていたら 403 を返す
- **CSRF トークンの判定は、Cookie でログインを確認したリクエストだけに行う**。Web アプリはトークンを `X-CSRF-Token` ヘッダーで送る
- **前提として、`GET` ではデータを変更しない**

### CSRF トークンの仕組み

| 状態 | 照合の仕方 | DB への処理 |
|---|---|---|
| ログイン前 | サーバーの秘密鍵（環境変数 `CSRF_SIGNING_KEY`）で署名した Cookie と、ヘッダーで送られたトークンを照合する（署名付きダブルサブミット Cookie） | なし |
| ログイン後 | セッションの行に保存したトークンと、ヘッダーで送られたトークンを照合する | 読み込みだけ |

- **`GET /api/csrf-token` が唯一のトークンの受け取り口**。ログイン中なら今のセッションのトークンを返し、未ログインなら署名付き Cookie を発行してログイン前のトークンを返す。Web アプリは、起動時・画面の再読み込み時など、手元のトークンを失ったときにこれを呼ぶ
- ログインに成功したら、正式なセッションと新しい CSRF トークンを発行する。ログイン前のトークンは引き継がない
- トークンは `crypto/subtle.ConstantTimeCompare` で照合する（比較にかかる時間から値を推測されないため）
- **CSRF トークンを返すレスポンスは圧縮しない**（圧縮後のサイズの変化からトークンを推測される BREACH 攻撃の対策）

### Cookie の属性

セッションの Cookie と、ログイン前の CSRF トークンの署名付き Cookie の両方に、次の属性を付ける。

| 属性 | 値 |
|---|---|
| `HttpOnly` | 付ける |
| `Secure` | 付ける |
| `SameSite` | `Strict` |
| 名前 | `__Host-` で始める（例：`__Host-session`）。これにより `Path=/`・`Domain` 指定なしが強制される |

### セッション ID と CSRF トークンの作り方・保存の仕方

| 項目 | 内容 |
|---|---|
| セッション ID | `crypto/rand` で 32 バイトの乱数を作る。DB には **SHA-256 のハッシュ値**を保存し、ID そのものは保存しない |
| CSRF トークン（ログイン後） | `crypto/rand` で 32 バイトの乱数を作り、セッションの行にそのまま保存する |

### セッションの管理

- **保存先は PostgreSQL のテーブル**
- **同時ログインは制限しない**。1 人のユーザーが複数の端末で同時にログインできる
- 期限切れの行は、API サーバーの中で 1 時間ごとに削除する。起動直後にも 1 回実行し、失敗してもログに残して次の回に再実行する
- 次の操作が行われたら、そのユーザーのセッションを削除する

| 操作 | 扱い |
|---|---|
| 管理者がユーザーを削除する | 全セッションを削除する |
| 管理者がパスワードをリセットする | 全セッションを削除する |
| 本人がパスワードを変更する | 変更した端末以外のセッションを削除する |
| ログイン失敗 5 回でロックされる | 削除しない |
| 管理者がロックを解除する / 名前・メールアドレスを変更する | 削除しない |

### その他

- **ログイン前に呼べる API（`GET /api/csrf-token`、両方のログイン API）には、nginx で同じ送信元からの呼び出し回数の制限をかける**。具体的な制限値は、ステップ 2-2 の実装時に決める（[ADR 0014](0014-login-logout-api-spec.md) で、制限の対象をログイン API の 2 つだけに変更し、制限値を決定した。本 ADR 末尾の追記を参照）
- 秘密鍵 `CSRF_SIGNING_KEY` は `.env` に置き、Git には入れない。未設定なら API は起動時に中止する
- **セッションと CSRF トークンの仕組みは、Go の標準ライブラリ（`crypto/rand`・`crypto/sha256`・`crypto/hmac`・`crypto/subtle`・`net/http`）で自前で作る**。外部のライブラリは使わない

## 検討した選択肢

**認証方式 — トークン方式（JWT）** — サーバーが記録を持たないため、本人確認で DB を引かずに済み、サーバーを大量に並べる構成や、複数のサービス・会社をまたいで同じログインを使う構成に強い。しかし、ログアウトしても発行済みのトークンは有効期限まで使え、管理者によるユーザーの削除やパスワードのリセットも、ログイン中の端末に即座には効かない。取り消しを実現するには結局サーバー側に記録を持たせることになり、セッション方式に署名の検証を足しただけの仕組みになる。本番プロジェクトの条件（API サーバーと PostgreSQL の構成、単一のサービス）では、トークン方式の強みが活きる場面がない。

**セッション ID の送り方 — Cookie だけ（Web 専用）** — 仕組みが 1 本で済み、作るものが最小になる。しかし本番では Web とモバイルが API を共通で使うことが確定しており、モバイルアプリは Cookie を自動で扱う仕組みを持たない。本番で必ず必要になる経路と、「Web には本文で返さない」などの決まりを、雛形の段階で先に形にしておくため採らなかった。

**セッション ID の送り方 — Web もヘッダーに統一する** — 仕組みが 1 本になり、ヘッダーはブラウザが自動で付けないため CSRF も成立しない。しかしヘッダーに付けるには、セッション ID を JavaScript から読める場所に保存する必要があり、XSS が起きると ID を外部に持ち出される。HttpOnly の Cookie ならスクリプトから読めない。OWASP も、セッション ID を localStorage に保存しないよう勧めている。モバイルアプリでは XSS の入り口がなく、Keychain / Keystore という安全な保存場所があるため、ヘッダーでも同じ問題は生じない。

**Web とモバイルの見分け方 — 同じパスで、リクエストに付けた目印で見分ける** — パスは 1 つで済む。しかし同じ処理の中で目印を見て分岐することになり、目印の付け忘れや分岐の書き誤りがそのまま「Web に本文でセッション ID を返す」穴になる。パスを分ければ、どちらの処理が動くかがパスだけで決まり、取り違えようがない。

**Cookie とヘッダーの両方が付いてきた場合 — どちらかを優先する** — 正しく作られたクライアントでは起こらない状況である。優先順位の決まりを持つと、「Cookie で本人を確認したのに、ヘッダー扱いになって CSRF の判定が飛ばされる」経路が生まれうる。一律に拒否すれば、どちらで本人を確認したかと、CSRF の判定をするかが常に一致する。

**CSRF 対策 — `Origin` の判定だけにする** — サーバー側の数行で済み、Web アプリ側の変更もいらない。しかし `Origin` の判定は「ブラウザが `Origin` を正しく付けること」に頼る対策で、古いブラウザや一部の拡張機能・プロキシでは付かない、または `null` になることがある。OWASP は CSRF トークンを基本の対策とし、`Origin` の確認は多層防御として重ねる補強に位置づけている。

**CSRF 対策 — CSRF トークンだけにする（ログイン後の API から `Origin` の判定を外す）** — トークンだけでも CSRF は防げる。しかしセオリーは基本の対策に補強を重ねる多層防御であり、トークンの発行や照合に不具合があった場合や、判定を入れ忘れた API があった場合に守りが消える。`Origin` の判定は追加のコストがほぼなく、将来のための機能ではなく今ある攻撃への対策のため、YAGNI にも当たらない。Web 用のログイン API では、モバイルアプリが誤って Web 用のパスを呼んだとき、その場で 403 として弾く役割も持つ。この役割はトークンでは代わりにならない。

**ログイン前の CSRF トークン — ログイン前用の仮のセッションを DB に作る** — OWASP がログイン CSRF の対策として挙げている方法で、ログイン後と同じ仕組みで照合できる。しかし、Cookie を持たずに発行 API を大量に呼ばれると、そのたびに DB へ 1 行書き込むことになり、ログインしていない誰でも DB の負荷を上げ、行を溜められる。呼び出し回数の制限をかけても、多数の送信元から分散して呼ばれると書き込みは積み上がる。署名付きの Cookie で照合すれば、ログイン前のリクエストで DB への書き込みが一切起きない。罠サイトは利用者の Cookie を読めず作れないため、ログイン CSRF への守りは弱まらない。

**CSRF トークンの再取得 — ブラウザの `sessionStorage` に保存する** — 再読み込みのたびに API を呼ばずに済む。しかし別のタブで開いた場合や保存に失敗した場合は値がなく、結局取り直す仕組みが必要になる。発行 API をログイン中にも使える形に広げれば、Web アプリは「トークンを失ったら 1 回呼ぶ」という 1 つの決まりで、どの場面でも正しいトークンを受け取れる。

**同時ログイン — 後勝ち・先勝ち・Web とモバイルで 1 つずつ** — いずれも、同時ログインを制限する要件がないため採らなかった。先勝ちは、ログアウトせずにブラウザを閉じると有効期限まで他の端末からログインできなくなる。セッションのテーブルにユーザー ID を持たせるため、制限が必要になった時点で、ログイン時に既存のセッションを削除する処理を足すだけで後から実現できる。

**アカウントロック時にセッションを削除する** — ロックは「新しいログインを止める」ための仕組みである。削除する扱いにすると、攻撃者がわざと 5 回失敗させるだけで、本人の端末を何度でも強制的にログアウトさせる嫌がらせができてしまう。

**`SameSite` 属性 — `Lax`** — リンクで画面を開いたときの `GET` にだけ Cookie を付ける設定で、画面の読み込みにログインを必要とする構成で意味を持つ。本プロジェクトの画面は nginx が配信する静的なファイルで、ログインを確認するのは画面が開いた後の同じサイトからの API の呼び出しだけのため、`Strict` にしても利用者の操作に影響がない。

**セッション ID のハッシュ化 — パスワードと同じ bcrypt** — bcrypt は、人が決める推測されやすいパスワードを総当たりから守るための「わざと遅いハッシュ」である。セッション ID は推測できない乱数のため総当たりが成り立たず、SHA-256 で十分である。セッション ID はリクエストのたびにハッシュ値を計算して照合するため、bcrypt を使うとすべての API が遅くなる。

**セッションの保存先 — Redis** — DB より速く、有効期限が来た行を自動で消すため片付けの処理がいらない。しかしコンテナを 1 つ追加して管理する必要がある。PostgreSQL はすでにあり、API サーバーを複数台にしても共有できる。

**期限切れの行の片付け — ログインのついでに、そのユーザーの行を消す** — 定期的な処理がいらない。しかしログインしなかった人の行や、ログインし直さない人の行が消えない。定期的に全体を掃除する形とした。削除は何度実行しても結果が同じになるため、API サーバーが複数台でそれぞれ実行しても問題は起きない。

**仕組みの作り方 — ライブラリ（`alexedwards/scs`、`gorilla/csrf` など）を使う** — 多くの利用者に使われ、不具合が直されてきた実績がある。しかし本 ADR のセキュリティの中身（ハッシュ値での保存、Cookie とヘッダーの両対応と両方付いたら 400、`Origin` の双方向の判定、パスワード変更時の他のセッションの削除など）は、どのライブラリにもそのままの形では入っておらず、ライブラリを使っても自前で書き足すことになる。ライブラリの前提と自前のコードを組み合わせると、守りが二重に掛かる箇所とどちらも掛かっていない箇所が生まれやすい。暗号の処理そのもの（乱数・ハッシュ・署名・一定時間での比較）は標準ライブラリの暗号部品を使い、自前で書くのは手順だけである。ライブラリが内部で行っている守りのうち、一定時間での比較と、トークンを返すレスポンスを圧縮しないことの 2 点は、本 ADR の決定に含めた。Go 1.25 以降の標準ライブラリにある `http.CrossOriginProtection` は、`Origin` などのヘッダーが付いていないリクエストを通す作りのため、「`Origin` がなければ 403」とする Web 用のログイン API の判定には使えない。

## 結果として生じること

- **REST のステートレスという原則からは、厳密には外れる。** ログイン状態をサーバー側に持つためである。ただしセッションを API サーバーのメモリではなく PostgreSQL に置くため、「どのサーバーでも同じリクエストを処理できる」という原則の目的は満たしている。URL の設計や HTTP メソッドの使い分けといった REST API の設計は変わらない。
- **ログインが必要な API は、リクエストのたびに DB を 1 回引く。** セッション方式である以上避けられない。
- **`GET` でデータを変更する API を作ってはいけない。** `GET` は CSRF トークンと `Origin` の判定の対象外であり、データを変更する `GET` はそのまま CSRF の穴になる。ブラウザは同じドメインへの `GET` に `Origin` を付けないため、`GET` に判定を入れると Web アプリ自身が弾かれる。
- **`Origin` の判定は、ブラウザ以外の道具から意図的に `Origin` を付けて送られたリクエストは防げない。** 防げるのは、利用者のブラウザを悪用する攻撃（CSRF）と、クライアントがパスを取り違えた呼び出しである。ブラウザ以外から直接 API を呼ぶ攻撃者に対しては、パスワードの照合とアカウントロックが守りになる。この判定を不正アクセス全般への守りとして当てにしてはいけない。
- **`curl` などで Web 用の API を試すときは、`Origin` ヘッダー（`-H 'Origin: https://myapp.local'`）を付ける必要がある。** 付けないと 403 になる。モバイル用のログイン API を試すときは、逆に `Origin` を付けてはいけない。
- **Web アプリは、手元の CSRF トークンを失ったら必ず `GET /api/csrf-token` を呼ぶ。** Flutter Web は画面を再読み込みするとメモリ上の値が消えるため、起動時にこれを呼ばないと、ログインは続いているのにパスワード変更やログアウトが 403 になる。
- **第一段階で作成済みの API（ユーザーの削除、パスワードのリセット）に、そのユーザーのセッションを削除する処理を足す。** 本人によるパスワード変更では「変更した端末以外」を削除するため、処理の中で今のリクエストのセッションを判別できる必要がある。
- **ログイン API は、ログイン前でも DB を読み、パスワードの照合（bcrypt）を行う。** ログイン前の CSRF トークンの発行では DB に書き込まないが、ログイン API そのものは重い処理のため、nginx での呼び出し回数の制限が欠かせない。
- **環境変数 `CSRF_SIGNING_KEY` が必須になる。** 各自が `.env` にランダムな値を設定する手順を、[local-https-setup-guide-for-mac.md](../local-https-setup-guide-for-mac.md) の手順 5 に追加した。値を変えると、そのときログイン画面を開いていた人のログイン前の CSRF トークンだけが無効になる。ログイン済みのセッションは秘密鍵を使っていないため影響を受けない。
- **外部依存は増えない。** [ADR 0003](0003-backend-database-access-and-routing.md) の「外部依存を `pgx` と `golang.org/x/crypto` の 2 つに限定する」状態が保たれる。ただしこれは結果であり、ライブラリを使わない理由ではない（理由は「検討した選択肢」のとおり）。
- **自前で作る代わりに、本 ADR の決定を 1 項目ずつ自動テストで確かめる。** ライブラリの利用実績に頼らない分、決定したとおりに動いていることをテストで担保する。

## 追記：ステップ 2-2（ログイン・ログアウトの API の仕様）の策定にともなう変更

ステップ 2-2 の仕様を固める過程で、本 ADR の内容に 1 点の変更が生じた。経緯は [0014-login-logout-api-spec.md](0014-login-logout-api-spec.md) に記録している。

**nginx の呼び出し回数の制限は、ログイン API（`POST /api/login`・`POST /api/mobile/login`）の 2 つだけにかけ、`GET /api/csrf-token` は対象外とする** — `GET /api/csrf-token` は DB に書き込まず、署名の計算だけで終わり、`/api/health` と同程度に軽い。本 ADR でも、制限が「欠かせない」理由として挙げていたのは、ログイン API が bcrypt を実行する重い処理であることだった。制限値は、2 つのログイン API を合わせて、同じ送信元から 1 秒に 1 回（一時的な超過の許容 60 回）とした。
