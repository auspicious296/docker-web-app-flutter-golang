# ログイン状態の保持期間と、ユーザー CRUD をログインで制限しないこと

ステップ 2-1 のうち、[ADR 0012](0012-session-based-authentication.md) で対象外とした 2 項目を決めた。**ログイン状態の保持期間は Web とモバイルで分け、Web はアイドル 30 分 / 絶対 8 時間、モバイルはアイドル 30 日 / 絶対 90 日とする。**値は `compose.yaml` に置き、コードには書き込まない。**第一段階のユーザー CRUD（画面・API）は、ログインによる制限をかけない。**

- **アイドルタイムアウト**：最後の操作から一定時間が経つと、ログイン状態が切れる
- **絶対タイムアウト**：ログインから一定時間が経つと、操作していてもログイン状態が切れる

## 決定した内容

### 保持期間

| クライアント | アイドルタイムアウト | 絶対タイムアウト |
|---|---|---|
| Web アプリ（`POST /api/login` でログイン） | 30 分 | 8 時間 |
| モバイルアプリ（`POST /api/mobile/login` でログイン） | 30 日 | 90 日 |

- どちらのログイン API を通ったかを、セッションの行に記録する。保持期間は、この記録に応じた値で判定する

### 値の置き場所

- 4 つの値は、`compose.yaml` の `api` の `environment` に環境変数として書く。コードには書き込まない
- 書式は Go の `time.ParseDuration` に従う。**日の単位がないため、日単位の値は時間に換算して書く**（30 日は `720h`、90 日は `2160h`）
- **値が設定されていなければ、API は起動時に中止する。**コードに初期値を持たせない

### Web の Cookie の有効期限

- セッションの Cookie（`__Host-session`）には有効期限を付けない。ブラウザを閉じると Cookie が消える

### 最後の操作日時の更新

- セッションを確認したすべてのリクエスト（`GET` を含む）で、セッションの行の最後の操作日時を毎回更新する
- セッションの確認と最後の操作日時の更新は、1 つのクエリ（`UPDATE ... RETURNING`）で行う

### ユーザー CRUD の制限

- 第一段階のユーザー CRUD の画面・API には、ログインによる制限をかけない。今のまま誰でも操作できる
- **第一段階と第二段階は、別々の試験用プログラムとして扱う。**両者の接点は、第一段階で作成したユーザー情報を第二段階のログインに使うことだけである

## 検討した選択肢

**ユーザー CRUD — ログインしていれば誰でも操作できるようにする** — `users` テーブルには管理者と一般ユーザーを区別する列がない。このため、一般ユーザー全員が管理者と同じ操作をできることになり、ロードマップの「一般ユーザーは一覧・登録・削除・ロック解除ができない」と矛盾する。

**ユーザー CRUD — 管理者の区別を設け、管理者だけが操作できるようにする** — ロードマップの操作範囲の表と一致する。しかし、権限の列の追加、管理者かどうかの判定、最初の管理者の作り方（登録は管理画面からしかできないため、管理画面にログインが必要になると最初の 1 人を登録できない）を決める必要があり、第二段階の範囲が広がる。第一段階は「認証部分を意図的に外した実験用の画面」であり、第二段階のゴールは「ログインしてマイページを表示する」までのため採らなかった。

**保持期間 — Web とモバイルで共通にする** — 仕組みは 1 つで済む。しかし、Web に合わせて短くするとモバイルアプリで頻繁にログインし直すことになり、モバイルに合わせて長くすると Web のセッションが長く残る。Web のセッション ID は共用の PC などのブラウザに残る可能性がある一方、モバイルアプリのセッション ID は端末の Keychain / Keystore に保存される。また、モバイルアプリの利用者は、ログインしたままの状態が長く続くことを期待する。本番では両方のクライアントが同じ API を使うため、雛形の段階で分けておく。

**Web の値 — アイドル 15 分 / 絶対 8 時間、アイドル 2 時間 / 絶対 24 時間** — OWASP の Session Management Cheat Sheet は、アイドルタイムアウトの目安をリスクの低いアプリで 15〜30 分、絶対タイムアウトの目安を 4〜8 時間としている。マイページで行える操作は自分の情報の表示とパスワードの変更だけで、重要度が低いため、目安の範囲内で利便性の高い側（30 分 / 8 時間）を選んだ。15 分は少し席を外しただけでもログインし直すことが増え、2 時間 / 24 時間は目安を超える。

**モバイルの値 — アイドル 7 日 / 絶対 30 日、アイドル 90 日 / 絶対 365 日** — モバイルアプリには OWASP に具体的な目安がない。7 日 / 30 日は、ふだん使う利用者でもログインし直す場面が多くなる。90 日 / 365 日は、端末を紛失した場合やアプリを使わなくなった場合に、セッションが長く残り続ける。30 日 / 90 日であれば、ふだん使う利用者がログインし直す場面はほとんどなく、使われなくなったセッションが残るのも最長 1 か月で済む。

**値の置き場所 — `.env` に置く** — 各自の手元で自由に変えられる。しかし Git で管理されないため、開発者ごとに値が食い違っていても気づけず、`.env.example` に値を追加しても、すでに `.env` を作成済みの人には反映されない。保持期間は秘密の値ではなく、チーム全体で揃えるべき値であり、この性質はすでに `compose.yaml` に置いている `TZ` と同じである。

**値の置き場所 — 未設定の場合に備えて、コードに初期値を持たせる** — 設定し忘れても API が起動する。しかし、それでは結局コードの中に値が混ざる。未設定なら起動時に中止する扱いは、`CSRF_SIGNING_KEY` と同じである。

**Web の Cookie — 有効期限を付ける（ログインから 8 時間後まで残す）** — ブラウザを閉じて開き直しても、ログインしたままでいられる。しかし、ブラウザを閉じればログインし直しになると利用者が期待している場面でもログイン状態が残り、共用の PC での危険につながる。アイドルタイムアウトが 30 分と短いため、有効期限を付けても、ブラウザを開き直したときにログインしたままでいられる場面は限られる。

**最後の操作日時 — 前回の更新から一定時間以上経っている場合だけ更新する** — 書き込みの回数が減る。しかし、アイドルタイムアウトの判定に最大でその間隔分の誤差が出るうえ、間隔の値という設定値が 1 つ増える。利用者が多く書き込みの負荷が問題になる規模で効く工夫であり、本プロジェクトの規模では得られるものがない。毎回更新しても、DB への問い合わせは 1 回のままである。

## 結果として生じること

- **第二段階のログインは、仕組みを試すためのものであり、守りにはならない。**ログインしていなくても、第一段階の `PUT /api/users/{id}/password` で他人のパスワードをリセットし、その人としてログインできるためである。
- **ログインが必要な API では、リクエストのたびに DB へ書き込みが発生する。**最後の操作日時を毎回更新するためである。
- **ブラウザに前回の状態を復元する設定（Chrome の「前回開いていたページを開く」など）があると、ブラウザを閉じても Cookie が残る場合がある。**その場合も、サーバー側のアイドルタイムアウト・絶対タイムアウトの判定で切れる。
- **保持期間の値を変えたら、`docker compose up -d` で API のコンテナを作り直す必要がある。**環境変数は、コンテナの起動時に読み込まれるためである。
- **指定できる値の上限は、Go の `time.Duration` の範囲（約 106,751 日、約 292 年）である。**Web の Cookie には有効期限を付けないため、ブラウザが Cookie の有効期限を最長 400 日で打ち切る制限は関係しない。
