# ユーザー登録画面の入力検証

ステップ 1-5 のユーザー登録画面について、**パスワードに使える文字を ASCII の印字可能文字（スペースを除く）に限り、入力検証はクライアントとサーバーの両方に置き、メールアドレスの重複（409）は項目別のエラーとして入力欄の直下に表示する**ことを決めた。画面の実装に着手する前に決めたのは、1 つ目が API とデータの両方に影響する決定であり、残る 2 つが Flutter 側の `UserFailure` と `ApiErrorDto` の形を決めてしまうためである。

## 検討した選択肢

**パスワードの文字種 — 制限しない（ステップ 1-4 の実装）** — ステップ 1-4 の `validatePassword` は、空・8 文字未満・72 バイト超過だけを見ており、日本語も絵文字も受け付ける。72 バイトという上限は bcrypt が 73 バイト目以降を無視することに由来する技術的な制約であって、利用者に向けた仕様ではない。この形を画面に持ち込むと、**同じ「8 文字以上」という条件が、英数字なら 72 文字まで、日本語なら 24 文字まで**という二重の上限になる。実際、`handler/errors.go` の文言は「パスワードは 72 バイト以内で入力してください（日本語の場合は 24 文字まで）」という、利用者に理解を求める一文になっていた。入力欄のプレースホルダーにも同じねじれが現れるため、採らなかった。

**パスワードの文字種 — 半角英数字のみ（記号を許さない）** — 説明は最も短くなるが、パスワードに使える文字を減らすことは強度を下げる方向の変更であり、利用者に不利益だけを与える。採らなかった。

**入力検証の置き場所 — クライアントだけで検証する** — 通信の前にすべて弾ける代わりに、ルールの記述が Dart 側と Go 側の 2 箇所に分かれたまま、画面が「自分が正しい」ように振る舞うことになる。片方だけを直したときに黙ってずれ、ずれた結果はサーバーが返す 400 になるが、その 400 を項目別に表示する経路がなければアラートに落ちる（どの項目が悪いか分からなくなる）。

**入力検証の置き場所 — サーバーだけで検証する** — ルールの記述は 1 箇所に収まるが、8 文字未満のような自明な誤りでも 1 往復の通信とローダーが走る。また、パスワードと確認用の一致は API が知らないルールであるため、これだけは必ずクライアントに残る。

**メールアドレスの重複（409）— アラートダイアログで知らせる** — 「登録処理の失敗はアラート」という素直な切り分け。しかし 409 は**入力を直せば解決する失敗**であり、利用者が次に取る行動はメールアドレスの入力し直しである。アラートに出すと、OK を押して閉じたうえで、どの欄を直すのかを文面から読み取らせることになる。

**409 の文言 — Flutter 側が持つ** — API は衝突相手が生きているか削除済みかでコードを分け（`email_already_exists` / `email_belongs_to_deleted_user`、ADR 0004）、それぞれに日本語の文言を付けている。Flutter 側に同じ文言を持たせると、サーバーにしか判定できない事柄の説明が 2 箇所に分かれる。

## 結果として生じること

- **パスワードの上限は「72 文字」になり、バイト数という概念が画面から消える。** `MaxPasswordBytes`（バイト）は `MaxPasswordLength`（文字）へ置き換わり、理由コード `ReasonTooManyBytes` は `ReasonTooLong` に統合される。文字種の検証と、その理由コードが 1 つ増える。
- **この変更は `PUT /api/users/{id}/password`（パスワードリセット）にも同時に効く。** 検証は `service` の 1 つの関数に集約されているためである。
- **日本語のパスワードは登録できなくなる。** ステップ 1-4 の API で登録済みのユーザーがいる場合、そのパスワードは DB に残るが、同じ値を画面から再設定することはできない。
- **文字種の制限を後から厳しくすることはできない。** 第二段階でログインを実装した後に制限を狭めると、既存のユーザーがログインできなくなる。緩める方向（日本語を許すなど）は、いつでも安全に行える。
- **検証のルールと文言が Dart と Go の 2 箇所に存在する。** ずれた場合はサーバーが弾き、その 400 の `fields` が入力欄の直下に表示される（黙って通ることはない）。Dart 側のルールは `domain/` に置き、登録・編集・パスワードリセットの 3 画面で共用する。
- **`ApiErrorDto` は `code` と `fields` を画面まで運ぶ必要がある。** ステップ 1-5 の一覧画面までは `message` だけを読み、`fields` は「一覧画面では使わない」として持たせていなかった。`UserFailure.api` も `code` を併せ持つ形になる。
- **アラートダイアログが出たかどうかが、そのまま「入力の問題か、環境の問題か」の区別になる。** 入力を直せば解決する失敗（検証エラー・409）はすべて入力欄の直下に出るため、アラートに現れるのは通信の失敗・応答形式の異常・サーバー内部エラーだけになる。
- **API が知らない `field` を返した場合に備える必要がある。** 入力項目は enum で表し、enum に変換できない `field` はアラートへ回す。変換できないものを捨てると、エラーが 1 つも表示されないまま登録できない状態になり得るためである。
- **登録（POST）は応答の本文を解釈しない。** 登録完了のダイアログにはユーザー名もメールアドレスも表示しないため、201 が返った時点で成功として扱える。`UserApiClient._decode` は 200 のみを成功とみなす実装のため、201 を成功として扱う対応が必要になる。
