# ユーザー情報削除画面の成否不明時の扱いと 404 の伝え方

ステップ 1-5 のユーザー削除について、**確認ダイアログではなく専用画面で行い、成否不明のときは一覧へ戻って再読み込みし、404 は「失敗」ではなく「すでに削除済み」として伝える**ことを決めた。1 つ目はロードマップの記述（「確認ダイアログを表示する」）を変える判断で、2 つ目はパスワードリセット画面（[0010](0010-user-password-reset-screen.md)）と**逆の結論**になった箇所である。

基本の動作・レイアウト・検証・ローダーは登録画面（[0008-user-create-screen.md](0008-user-create-screen.md)）、画面を開いたときの取得と対象ユーザーの表示はパスワードリセット画面（[0010](0010-user-password-reset-screen.md)）を踏襲する。以下は、踏襲**できなかった**点と、この画面で新たに生じた点だけを記録している。

## API の実装から分かったこと

```sql
UPDATE users SET deleted_at = now(), updated_at = now()
  WHERE id = $1 AND deleted_at IS NULL
  RETURNING ...
```

- **削除は冪等ではない。** 削除済みの行は 0 行になるため、同じユーザーに 2 回実行すると 2 回目は 404 が返る。パスワードの上書き（何度実行しても結果が同じ）との決定的な違いである。
- **成功時は削除後のユーザーを 200 で返す。** `deleted_at` と `updated_at` が入った状態で返るため、一覧が削除済みの行を表示している場合は 1 行差し替えで表示を最新にできる。
- **404 のレスポンスにユーザーは含まれない。** そのため 404 の経路では 1 行差し替えができず、一覧を取り直すしかない。
- **リクエストボディを送らない。** `validation_error`（400 の `fields`）を返す経路が存在しない。

## 検討した選択肢

**削除の入口 — 一覧に確認ダイアログを出す（ロードマップの当初の記述）** — ロック解除と同じく画面遷移なしで完結する。しかし削除は取り返しがつかない操作であり、「はい」を 1 回押すだけで確定する形は、ロック解除（やり直せる）と同じ重さの操作に見えてしまう。**専用画面にすると、遷移・語の入力・確認ダイアログという 3 つの段階を踏ませられる**うえ、対象のユーザー名とメールアドレスを画面いっぱいに示して誰を消すのかを確認させられる。

**成否不明のとき — 画面に留まって再実行を促す（パスワードリセット画面と同じ）** — 0010 は「冪等だから押し直すことが最も確実な確認手段になる」「一覧に戻っても `password_hash` は表示されず目で確認できない」の 2 点を理由に画面へ留まる判断をした。**削除ではこの 2 点が両方とも逆になる。** 削除は冪等でないため、実際には成功していた場合に押し直すと 404 が返り、「削除に失敗しました」と誤解させる。一方、一覧に戻れば削除済みの表示か行の有無で管理者が自分の目で確かめられる。0010 の理由を機械的に当てはめると、この画面では逆の結果を生む。

**一覧への指示 — ルートの `onExit` に一本化する（パスワードリセット画面と同じ）** — 0010 が `onExit` へ寄せたのは、成否不明で画面に留まる仕様のため「離脱そのものが一覧への指示になる」状況が生まれ、`context.pop` の戻り値では**ブラウザの戻るボタンを通る経路を拾えない**ためだった。上で成否不明も一覧へ戻す判断をしたことで、この画面は成功・404・成否不明のいずれでも**自分で `pop` を呼ぶ**ようになり、その状況が消えた。`onExit` を使うと、一覧の再読み込みを起こす場所が一覧画面とルートに分かれたままになる。

**404 の伝え方 — 「削除に失敗しました」と出す** — 他の失敗と同じ扱いにできる。しかし実際にはそのユーザーは削除済みであり、**事実と異なる内容を伝えることになる**。そのまま一覧へ戻った管理者は、削除されているものを削除されていないと認識したまま作業を続ける。もう一度削除しようとしても、一覧では削除済みの行の「削除」ボタンが無効なので押せずに戸惑う。ADR 0004 は、すでに解除済みのユーザーにロック解除を実行してもエラーにしない理由を「結果として望む状態になっているため」と整理している。**404 で削除が返る場面も、望む状態が成立している点は同じ**である。

**404 の文言 — 「他の操作によってすでに削除されています」** — 誰の操作かを書かないと、管理者が**自分の操作を疑う**（「他の操作？ 自分が何か変なことをしたのか？」）。削除を実行した直後に失敗を思わせる表示が出る場面であり、不安を増やす方向に働く。

**取得の失敗 — 理由を問わず一覧を再読み込みする** — 実装は分岐がなく最も軽い。しかしここで見るべきは「**そのユーザーの削除状態**について一覧が実態と食い違っている可能性」であり、それを示すのは 404 だけである。通信エラーと応答形式エラーは回線や API 側の問題で、削除状態については何も語らない。これらまで再読み込みの理由に含めると、「どの画面のどんな失敗でも一覧を再読み込みすべき」という話になり、判断の基準として成立しなくなる。

**検証エラーの保持 — 共有の `UserFormField` に `deleteConfirmation` を足す** — 他の 3 画面と状態の形が揃う。しかしこの enum の役目は **API が返すフィールド名と画面の欄を対応付けること**で、削除確認入力は API に一切送らず、削除画面にしか存在しない。3 画面はエラー後のフォーカス移動でこの enum を先頭から順になめるため、自分の画面に存在しない項目を毎回通過することになる。**1 画面にしか存在しない項目を共有リストに入れると、共有している理由がなくなる。**

**検証エラー後 — 入力欄をクリアする（登録画面のパスワード欄と同じ）** — 打ち直しの手間が増える分ゲートとしては強くなる。しかし登録画面がパスワードをクリアする理由は「検証を通らなかった値を伏せ字の裏に残さない」ことで、伏せ字であることが根拠だった。削除確認入力は伏せ字ではない。さらに**エラーになるのは目に見える誤りだけ**（前後の空白は照合前に除かれる）なので、入力を消すと**案内文の語と見比べて直す手がかりを奪う**ことになる。この欄の目的は「誤って削除画面に来た管理者がそのまま削除するのを防ぐ」ことであり、一度でも語を打とうとした時点でその目的は果たされている。

**照合 — 大文字・小文字を区別しない** — `CONFIRM` と打っても通る。しかし画面には案内文とプレースホルダの両方に小文字で `confirm` と示しており、大文字で打った管理者が「指示どおり打ったのに通らない」と考える根拠がない。大文字は入力欄を見れば分かるため、自力で直せる。

**URL — `/users/{id}`（削除 API と同じ形）** — パスワードリセットは `/users/{id}/password` として API のパスに揃えた。しかし削除の API は**メソッド（DELETE）で操作を区別**しており、パスに操作名が入らない。URL にはメソッドがないため、この形では削除画面であることが読み取れない。`/users/new` と同じ 2 セグメントの形にもなり、ID の位置に操作名が来る形を作ることになる。

**遷移 — `go` に変えて URL をアドレスバーに出す** — `push` で開いた画面は go_router の `ImperativeRouteMatch` になり、**アドレスバーの URL に反映されない**（`RouteMatchList.uri` の定義による）。`go` に変えれば出るようになり、リロードでの復元やブックマークもできる。しかし `context.pop` の戻り値を受け取る相手がいなくなるため、一覧への指示を `onExit` 方式に戻すことになる。削除画面は**一覧で行を選んでからでないと来られない画面**で、URL 単独で開いて使う場面がない。

## 結果として生じること

- **同じ「成否不明」に対して、パスワードリセット画面と削除画面が逆の振る舞いをする。** 前者は画面に留まり、後者は一覧へ戻る。**これは不揃いではなく、冪等かどうかの違いから導かれた結果である。**0010 を読んで「揃えるべきだ」と直すと、削除では押し直しが 404 を招く状態に戻る。
- **`pop` の戻り値方式に戻る。** 編集画面と同じく `UserDeleteResult`（`deleted(User)` / `reloadNeeded()`）を返し、一覧画面が受け取って反映する。一覧を書き換えるのは一覧画面だけ、という構図が保たれる。
- **完了ダイアログの文言だけ、削除画面が一覧の状態を読む。** 削除済みを表示中なら 1 行差し替えで済み、非表示中は取り直すため、ダイアログの文面が変わる。判定に使う `includeDeleted` は**ダイアログを組む直前に読むだけ**で、書き換えはしない。URL のクエリや `extra` で運ぶ案は、URL の手書き換えやリロードで値が壊れる経路を新たに作るため採らなかった（`extra` は `extraCodec` を設定しない限りリロードで復元されない）。
- **この画面のルートに `onExit` がない。** 削除処理では破棄して困る入力がないため離脱確認を出さず、一覧への指示も `pop` で返すため、ルート側ですることがない。登録・編集・パスワードリセットの 3 ルートはいずれも `onExit` を持つので、この画面だけが例外になる。
- **一覧の `_load` に「空になったページの是正」が入る。** 取得結果が 0 件・総件数が 0 でない・1 ページ目でない、の 3 つが揃ったら 1 つ前のページを読み直す。**削除はこの画面で唯一、一覧の総件数が減る操作**であり、そのページの最後の 1 件を消すとページ番号が古くなる。是正しないと、テーブルが空なのに「20 件中 21〜20 件」という表示になる。総件数が 0 のときに発動しないのは、既存の「0 件」「該当するユーザーがいません」の表示がそのまま正しいためで、1 ページ目で発動しないのは 0 ページ目を要求しないための歯止めでもある。判定を `_load` に置いたため、「一覧再読み込み」や「削除済みも表示」の切り替えなど**一覧のすべての取得経路に効く**。読み直しは 1 回だけとしている（削除は 1 件ずつのため、ずれるのは最大 1 ページ）。
- **検証エラーは文字列 1 つで持つ。** `Map<UserFormField, String>` が必要だったのは API が返した複数の検証エラーを欄ごとに振り分けるためだが、`DELETE` はボディを送らないので振り分ける相手が存在しない。共有の `UserFormField` は 4 項目のまま変わらない。将来この画面に入力欄が増えたら、そのとき対応表の形に作り直す。
- **未入力と誤入力でエラー文言を分けない。** どちらも管理者がすべきことは「`confirm` と入力する」の 1 つで同じであり、2 種類にすると意味のない違いを探させることになる。
- **照合は `trim()` してから完全一致。** `trim()` が除くのは Unicode の空白すべてで、全角スペース（U+3000）・タブ・連続した空白・BOM も含まれる。途中の空白は除かないため `con firm` は通らない。規則は「**目に見えない差異は救い、目に見える差異は救わない**」に整理できる。
- **取得の 404 と削除実行の 404 で、言い方を変える。** 実行時は「すでに削除されています」と断定する（取得に成功しているため、対象が存在したことは確実で、その後に消えた以外にありえない）。取得時は「すでに削除された可能性があります」と含みを持たせる（一度も取得できていないため、もともと存在しない ID だった可能性が残る）。
- **「削除する」ボタンだけ赤 `0xFFD32F2F`。** 他の 3 画面の実行ボタンは青（`0xFF0277BD`）だが、**取り返しのつかない操作であることを押す前に伝えられる要素が、この画面ではボタンの色だけ**である。エラー表示と同じ赤になるが、位置と形が違う（入力欄直下の小さな箱と枠線 / フォーム下端中央の塗りつぶしボタン）ため取り違える場面がない。
- **`ViewModel` 層のテストを 20 件追加した**（削除画面に 16 件、一覧の空ページ是正に 4 件）。
