# ユーザー一覧のテーブル表示に data_table_2 を採用する

ステップ 1-5 で作るユーザー一覧のテーブル表示に **`data_table_2`**（BSD-3-Clause）を採用し、バージョンは**最新の 3.0.0 ではなく 2.8.0** に固定する。Flutter 標準の `DataTable` / `PaginatedDataTable` でも作れるが、**ヘッダー行の固定と、左端の列の固定**の 2 点で手当てが必要になるためである。画面に着手する前に決めたのは、テーブルのウィジェットの API が View と ViewModel の両方の書き方を決めてしまい、後から差し替えると一覧画面を書き直すことになるからである。

## 検討した選択肢

**Flutter 標準の `DataTable` / `PaginatedDataTable`（追加パッケージなし）** — 列ヘッダー、ソートの矢印、行の選択を標準で持ち、列の中にボタンを置くこともできるため、一覧画面の要件の大半は標準だけで満たせる。採らなかった理由は 3 点。①縦スクロール時に**ヘッダー行が固定されない**（テーブルの一部として一緒に流れる）、②横スクロール時に**左端の列が固定されない**、③`PaginatedDataTable` に行を供給する `DataTableSource.getRow()` が**同期のメソッド**であり、ページごとにサーバーへ問い合わせる本プロジェクトの API（`?page=` / `?per_page=`）と素直につながらない。`data_table_2` はこの 3 点を補うことを目的としたパッケージで、③には `AsyncPaginatedDataTable2` が用意されている。なお `data_table_2` は Flutter 2.1 当時の標準 `DataTable` のソースコードから派生しており **API がほぼ同じ**であるため、標準で作ってから乗り換えることも、その逆も容易である。この後戻りのしやすさも採用の理由になっている。

**`trina_grid`（MIT）** — 列ごとのフィルタ、セルの編集、キーボード操作を組み込みで持ち、機能面では最も充実している。採らなかった理由は 2 点。①**この系統は一度、保守が途切れている**。前身の `PlutoGrid` の保守が止まった後に別の個人が引き継いだ経緯があり、利用者の 6 割近くが今も前身に残っている（月間ダウンロードは `PlutoGrid` 34.4k に対し `trina_grid` 26.2k、合算しても `data_table_2` の 183k の 3 分の 1）。②見た目と操作の作法が独自で、Material の外観から離れる。学習用テンプレートとしては、標準に近い形を残したい。

**`syncfusion_flutter_datagrid`（商用）** — 機能（Excel 風のフィルタ、グループ化、エクスポート）も保守体制（2001 年創業・従業員約 3,000 名の企業、更新は数日単位）も候補中で最も充実している。採らなかったのは**ライセンス**による。利用には商用ライセンスか、無償の Community ライセンス（年間総売上 100 万 USD 未満・開発者 5 名以下・従業員 10 名以下・外部からの資金調達が累計 300 万 USD 以下を**すべて**満たすこと。政府関連機関は対象外）が必須である。本プロジェクトは開発テンプレートであり、**これを使う側のすべての組織にこの条件が及ぶ**ため、採用しない。

**`material_table_view`（MIT）** — 任意の列の凍結、行の展開、大量データの仮想化を持つ。**最終公開が 13 ヶ月前**で更新が止まっており、月間ダウンロードも 7,620 と小さい。

**`davi`（MIT）** — ピン留め列、複数キーのソート、セルの結合を持ち、更新は候補中で最も活発。ただし月間ダウンロードが 1,370 と `data_table_2` の 1% に満たず、利用実績が乏しい。

**`data_table_2` の最新版 3.0.0** — 3.0.0 は 2.8.0 のわずか 4 日後に公開された版で、**機能の追加は 1 つもない**。変更点は Material の取り込み元を、`package:flutter/material.dart`（Flutter SDK 本体）から **`material_ui`**（Flutter 公式が Material を SDK から切り出した別パッケージ）へ全面的に差し替えたことだけである。SDK 制約（Dart 3.13 以上 / Flutter 3.47 以上）は 2.8.0 と一字一句同じであり、**2.8.0 は「古い版」ではなく、SDK の Material を使う最後の版**である。

採らなかったのは、`material_ui` が **SDK の Material を再エクスポートしていない**ためである。両者は同じ Material の独立した 2 つのコピーで、`Theme` / `Material` / `MaterialLocalizations` / `DataCell` などはいずれも**同名の別型**になる。実際に動かして確認した結果は次のとおり。

- **一覧画面だけで 3.0.0 を使う「部分採用」は成立しない。** 静的解析（`flutter analyze`）は問題なく通るのに、画面を開いた瞬間に `No Material widget found.` / `No MaterialLocalizations found.` で落ちる。SDK の `MaterialApp` が建てたツリーからは、`material_ui` 側の `Theme` や `Localizations` を解決できないためである。**コンパイルが通ってしまうぶん、実装してから初めて気づくことになる。**
- **アプリ全体を `material_ui` へ移すと、既存画面が壊れる。** SDK の `showDialog` が `No MaterialLocalizations found.` で落ち、SDK 側ウィジェットのテーマがすべて既定値（Material 3 のベースラインである紫）へ戻る。しかも**例外が出ないケースがある**ため、静的解析でも動作確認でも見落としやすい。
- **一覧画面だけを「島」として囲えば動く**（`Localizations` ＋ `material_ui` の `Theme` ＋ `Material` で包む。日本語化も機能する）。ただし `ThemeData` を SDK 側と `material_ui` 側の 2 系統で**二重管理**することになり、片方を書き忘れるとテーブルだけがアプリの配色を無視した既定色で描画される。このときも例外は出ない。

3.0.0 に機能上の利点がゼロである以上、型が分裂する実害だけを買うことになるため、2.8.0 に留める。

## 結果として生じること

- **保守は個人 1 名に依存する。** 未解決の Issue は 79 件あり、機能追加の要望が溜まっている状態である。ただし標準 `DataTable` の派生で規模が小さく、BSD-3-Clause であるため、保守が止まった場合はフォークするか標準の `DataTable` へ戻す判断ができる。この「引き返せること」が、機能の多い候補よりも優先した点である。
- **フィルタリングとソートの処理は自前で書く。** このパッケージが持つのは表示とスクロールの挙動だけで、絞り込みの仕組みは含まない。ソートもヘッダーの矢印と `onSort` のコールバックだけで、並べ替えそのものは実装する。
- **ヘッダーは 1 行しか持てない。** ヘッダーのセルに入力欄を置いて絞り込む形にする場合、見出しと入力欄を 1 つのセルに収めるか、入力欄をテーブルの外に置くことになる。
- **行の選択状態はウィジェットが保持しない。** `selected` で状態を与え、`onSelectChanged` で変更を受け取る形のため、選択中の行は ViewModel が持つ。View に状態を持たせない本プロジェクトの MVVM の方針とは一致する。
- **今後の機能追加やバグ修正は、3.x 系にしか入らない可能性が高い。** 2.8.0 と 3.0.0 の公開間隔が 4 日で、3.0.0 に機能差がないことから、作者は 3.x のみを保守する意向と見える。2.8.0 の時点で本プロジェクトに必要な機能は揃っているため当面は困らないが、修正が必要になった場合はフォークするか、アプリ全体を `material_ui` へ移して 3.x へ上げるかの判断になる。
- **SDK の `package:flutter/material.dart` が将来非推奨になった場合、この決定は見直す必要がある。** Flutter 3.47 時点では SDK 側の Material の実装がフルに残っており、非推奨化の予定は確認できていない。移行が必要になった時点で、**一覧画面だけではなくアプリ全体として** `material_ui` へ移り、あわせて `data_table_2` を 3.x へ上げることになる。
- **`AsyncPaginatedDataTable2` は使わない。** 却下理由の 3 つ目（同期の `DataTableSource` がサーバー側ページングと素直につながらない）を補うものとして挙げたが、実際には `DataTable2`（素）にページ送りの UI を自前で足す形を採る。`AsyncDataTableSource` が行の取得と選択状態を内部に抱え込み、ViewModel とは別に状態を持つ場所が生まれるためである。また、このウィジェットは行が選択されるとヘッダー帯が「N 件選択中」の表示に切り替わる作りで、テーブル直上に固定のボタンを並べる一覧画面の構成と領域が競合する。
- **このパッケージは pub.dev からではなく、改変版をリポジトリに取り込んで使っている。** 固定列を使うと、本体側が中央へ寄って固定列とのあいだに空白が開く問題があり、その原因がパッケージ内部にあって外から差し替えられないためである。取り込みの経緯と、それにより生じる保守の負担は [ADR 0007](0007-vendoring-data-table-2.md) に記録している。**本 ADR が決めているのは「どのパッケージを採用するか」までで、その取得元と改変の扱いは ADR 0007 が決める。**
- **`fixedLeftColumns` で固定した列には、`DataRow2.color` で指定した背景色が反映されない。** 固定列は本体とは別のテーブルとして描かれ、`color` がそちらへ渡されないためである（既定の選択ハイライトだけは反映される）。そのままでは、ロック中の行の左端だけが白く抜け、ロック中かつ選択中の行では左端が選択色・本体が薄い赤に食い違う。**行ごとの背景色は `color` ではなく `DataRow2.decoration` で指定する。** `decoration` は固定列にも渡されるため、左端の列もセルの端まで同じ色で塗られる。ただし `decoration` は行の区切り線ごと置き換えるため、罫線は `TableBorder` 側で引く必要がある。
- **BSD-3-Clause による義務は実質的に増えない。** Flutter SDK 自体が同じ BSD-3-Clause であり、配布時のライセンス表示は `showLicensePage`（依存パッケージの LICENSE を自動で収集して表示する仕組み）で満たせる。
- `data_table_2` は Flutter Favorites には選ばれていない。これは他の候補も同様である。
