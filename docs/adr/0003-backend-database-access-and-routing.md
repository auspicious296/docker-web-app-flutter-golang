# バックエンドの DB アクセス手段とルーティングの選定

ステップ 1-4 で実装するユーザー管理 API について、DB アクセスは **`pgx/v5` のネイティブインターフェース（`pgxpool`）**、ルーティングは **Go 標準の `net/http.ServeMux`** を採用し、外部依存を `pgx` と `golang.org/x/crypto`（bcrypt）の 2 つに限定する。`internal/` に 1 行も書かれていないこの時点で決めたのは、DB アクセス手段が `repository` 層のすべてのコードの書き方を決めてしまい、後から変えると同層の全面的な書き直しになるためである。

## 検討した選択肢

**DB アクセス — `database/sql` + `pgx/v5/stdlib`** — Go 標準のインターフェースを通す構成で、解説記事が最も多く、MySQL などへ乗り換える際はドライバの差し替えが効く。ただし本プロジェクトは ADR 0002 で PostgreSQL 固有の機能（`COLLATE "ja-JP-x-icu"`、`GENERATED ALWAYS AS IDENTITY`）を意図的に採用しており、乗り換えの際はいずれにせよ SQL の書き直しが発生する。pgx 公式は、PostgreSQL のみを対象とするアプリケーションにはネイティブインターフェースの利用を推奨している。「将来 MongoDB を併用する」という想定も選択の根拠にはならない。MongoDB の公式 Go ドライバは `database/sql` の上に載らないため、どちらを選んでも別ライブラリを追加することになり、差が出ないからである。なお `NULL` の扱いは、`database/sql` でも `*time.Time` を渡して受け取れるため、両者で大きな差はない。

**DB アクセス — `sqlx`** — `database/sql` に構造体マッピングを足したもので、一覧取得と 1 件取得が 2〜3 行短くなる。しかし pgx ネイティブにも `CollectRows` / `RowToStructByName` があり書き味の差は小さく、依存が 1 つ増えたうえで標準の層を 2 枚挟むことになる。

**DB アクセス — ORM（GORM）** — 論理削除を標準機能として持つ一方、ADR 0002 で Go 側の責務と明示した `WHERE deleted_at IS NULL` や `updated_at` の明示更新が SQL として現れなくなる。「DB 側では担保せず Go 側で担保する」という設計判断がコード上で見えなくなるため、学習用テンプレートとしては採らない。

**ルーティング — `chi`** — ミドルウェアの掛け分け（`Group` + `Use`）とルートのグループ化（`Route`）が書け、404 / 405 を JSON に揃える処理も専用のフックで数行で済む。一方、本プロジェクトのルートは第二段階まで含めて 11 本程度で、標準の `ServeMux` に 1 行ずつ書き並べれば足りる規模である。Go 1.22 以降の `ServeMux` は `GET /api/users/{id}` の形でメソッドとパスパラメータを扱えるため、機能面でも不足はない。

**ルーティング — `echo` / `gin`** — ハンドラの書き方がフレームワーク固有の型に変わる。`handler` → `service` → `repository` の層分けを標準ライブラリの流儀で学ぶという本テンプレートの目的から外れる。

**テスト — `repository` 層をモックで検証する** — `go-sqlmock`（`database/sql` 系）や `pgxmock`（pgx 系）で検証できるのは「自分が書いた SQL 文字列と、自分が期待した SQL 文字列が一致すること」だけであり、`WHERE deleted_at IS NULL` の書き忘れや `LIMIT` / `OFFSET` の計算違いといった本プロジェクトで最も壊れやすい箇所は素通りする。実 DB に接続するテストが本筋だが、テスト用 DB の用意・スキーマの適用・DB 未起動時のスキップという段取りが必要になるため、ステップ 1-4 では `service` 層のみをテストする。

## 結果として生じること

- **PostgreSQL 以外の DB へ乗り換える場合、`repository` 層を書き直すことになる。** `database/sql` を挟んでいないため、ドライバの差し替えでは済まない。
- **`database/sql` を前提とするライブラリ（`sqlx`、`go-sqlmock` など）は使えない。** モックが必要になった場合は `pgxmock` を使う。
- **すべてのクエリで `context` が必須になる**（`pool.Query(ctx, ...)`）。`database/sql` のような `ctx` なしの呼び出しは存在しない。
- **404 / 405 を JSON に揃えるラッパーを自前で書く必要がある**（20 行程度）。`ServeMux` は既定でプレーンテキストを返すため。
- **bcrypt のコスト値は `service` の設定値として持つ。** 本番の経路では `bcrypt.DefaultCost`（10）を、テストでは `bcrypt.MinCost`（4）を渡す。コスト 10 は 1 回あたり 50〜100 ミリ秒を要し、テストの実行時間に直結するためである。
- **`repository` 層のテストがないため、SQL の誤りは `curl` での確認で見つけることになる。** テスト用 DB の運用を決めた時点で、実 DB に接続するテストを追加できる。
- 外部依存は `github.com/jackc/pgx/v5` と `golang.org/x/crypto` の 2 つに収まる。
