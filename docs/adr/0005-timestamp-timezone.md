# 日時のタイムゾーンを JST に統一する

API・DB・pgAdmin の 3 者すべてで日時を **JST（`Asia/Tokyo`）** として扱う。具体的には、`compose.yaml` の `api` に `TZ: Asia/Tokyo` を設定し、DB 側にも既定のタイムゾーンとして `Asia/Tokyo` を設定する。API が返す日時は `2026-09-21T11:36:00+09:00` の形（RFC 3339）になる。一般的な作法である「サーバーは UTC で扱い、表示する側で変換する」からあえて外れているため、その理由を残す。

前提として、`TIMESTAMPTZ` は**タイムゾーンそのものを保存していない**。保存されるのは「いつという絶対的な瞬間」だけで、どのタイムゾーンで表示するかは読み出す側が決める。そのため表示の設定は 2 か所に分かれている。API のレスポンスとログは `api` コンテナの `TZ` が、pgAdmin の表示は DB 側のセッションのタイムゾーンが決める。**`api` にだけ `TZ` を設定しても pgAdmin の表示は変わらない。**

## 検討した選択肢

**すべて UTC のままにする（一般的な作法）** — サーバー側は UTC で一貫させ、JST への変換は表示する側（Flutter の `DateTime.parse().toLocal()`）に任せる。国際化に強く、「サーバーの時刻は常に UTC」という前提を疑わずに済む。採らなかったのは、**開発中に pgAdmin で値を確認する際、UTC 表示では実際の時刻と 9 時間ずれて読みにくい**という実際の不便があるためである。本プロジェクトは日本国内での利用を想定した学習用テンプレートであり、国際化の要求は現時点で存在しない。

**pgAdmin の表示だけを JST にする** — `compose.yaml` の `pgadmin` に `PGTZ: Asia/Tokyo` を設定すれば、pgAdmin からの接続だけが JST で表示され、API は UTC のままにできる。pgAdmin の読みにくさは解消するが、**API のレスポンスとログ（UTC）と、pgAdmin の表示（JST）が食い違った状態**になる。開発中に「いま見ている時刻がどちらなのか」を都度考えることになるため採らなかった。

**`api` にだけ `TZ: Asia/Tokyo` を設定する** — 最も手数が少ないが、上記のとおり pgAdmin の表示は変わらないため、食い違いは解消しない。

## 結果として生じること

- **DB に保存される値そのものは変わらない。** `TIMESTAMPTZ` は絶対時刻を保持しており、この決定が変えるのは表示の形式だけである。したがって、後から UTC に戻す場合もデータの移行は不要である。
- **日付の境界が JST 前提になる。** 「今日登録されたユーザー」のような日付での絞り込みを実装すると、その境界は日本時間の 0 時になる。この前提で書かれたコードが増えるほど、後から UTC へ戻す影響は広がる。
- **DB 側の設定は、DB を初期化し直さずに変更する必要がある。** `db` コンテナのボリュームは既に作成済みで、コンテナの `TZ` 環境変数は初期化時にしか効かないため、`ALTER DATABASE <DB名> SET timezone = 'Asia/Tokyo';` で設定する。
- **Go 側のコードは変わらない。** `time.Time` は絶対時刻を保持しており、比較や計算に影響はない。変わるのは JSON やログへ文字列として出力するときのオフセット表記だけである。
- **Flutter 側の実装も変わらない。** `DateTime.parse()` はオフセット付きの文字列をそのまま解釈できる。
- **国際化が必要になった時点で、この決定は見直す必要がある。** 日本以外の利用者が出てきた場合は、UTC で返して表示側で変換する形へ戻すことになる。
