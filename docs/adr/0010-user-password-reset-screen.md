# パスワードリセット画面の成否不明時の扱いと一覧への指示

ステップ 1-5 のパスワードリセット画面について、**成否不明のときは画面に留まって再実行を促し、一覧に対する指示はルートの `onExit` に一本化し、リセットしてもロックが残ることを完了ダイアログで赤字で伝える**ことを決めた。1 つ目と 2 つ目は登録画面・編集画面の形をそのまま使えなかった箇所で、3 つ目は API の実装を読んで初めて分かった事実に基づく。

基本の動作・レイアウト・検証・エラーの振り分けは登録画面（[0008-user-create-screen.md](0008-user-create-screen.md)）、画面を開いたときの取得は編集画面（[0009-user-edit-screen.md](0009-user-edit-screen.md)）を踏襲する。以下は、踏襲**できなかった**点と、この画面で新たに生じた点だけを記録している。

## API の実装から分かったこと

```sql
UPDATE users SET password_hash = $2, updated_at = now()
  WHERE id = $1 AND deleted_at IS NULL
```

- **`updated_at` が変わる。** パスワードのハッシュは一覧に出ないが、「更新日時」列は差し替えないと古いまま残る。当初「パスワードリセットなので選択行の表示更新は不要」と考えていたが、これは誤りだった。
- **`is_locked` と `failed_login_attempts` は変わらない。** ロック中のユーザーのパスワードをリセットしても、ロックは残る。
- **削除済みには効かない。** 画面を開いた後に削除されると 404 になる。

## 検討した選択肢

**成否不明のとき — 一覧へ戻って再読み込みする（登録画面・編集画面と同じ）** — 3 画面の挙動が揃う。しかしこの画面では 2 つの点で成り立たない。1 つは、API が `password_hash` を返さないため、**一覧に戻っても新しいパスワードが有効かどうか確認する手段がない**（編集画面は名前とメールアドレスが一覧に出るため目で確認できた）。分かるのは更新日時が変わったかだけで、それもリセット前の値を覚えている場合に限る。「更新されているかご確認ください」という案内が、実行できない指示になる。もう 1 つは、**パスワードの上書きが冪等である**こと。登録は繰り返すとユーザーが 2 人できるため一覧へ戻す必要があったが、同じ値で 2 回実行しても結果は「そのパスワードが設定されている」1 つに定まる。もう一度押すことが最も確実な確認手段であり、一覧へ戻すとその一手を封じたうえ入力も失わせる。

**成否不明のとき — 画面に留まってアラートだけを出す** — 押し直せて入力も残るが、実際には成功していた場合に**一覧の更新日時が古いまま残る**。これは上で「差し替えが必要」と決めた状態が、この経路にだけ残ることを意味する。

**一覧への指示 — `context.pop(値)` で返す（登録画面・編集画面と同じ）** — 編集画面は `UserEditResult` を `pop` の戻り値で返し、一覧が受け取って差し替えるか取り直すかを決めている。しかし `pop` の戻り値を渡せるのは**タイトルバーの「戻る」だけ**で、**ブラウザの戻るボタンでは値を渡せない**（go_router の `onExit` は「離脱してよいか」の真偽値しか返せない）。登録画面・編集画面では、値を返すのが「完了ダイアログの OK」と「404 のアラートの OK」だけ、つまり自分で `pop` を呼べる経路だけだったため、この差が問題にならなかった。**成否不明で画面に留まると決めたこの画面で初めて、「離脱そのものが一覧への指示になる」状況が生まれる。**

**ロックの扱い — API を変えて、パスワードリセット時にロックも解除する** — 管理者の操作は 1 回で済む。しかし 1 つのエンドポイントに 2 つの意味を持たせることになり、「パスワードだけ変えたいのにロックが外れた」を後から防げない。「ロック解除は専用のエンドポイントで明示的に行う」という ADR 0004 の整理を崩す。

**ロックの扱い — 何もしない** — 実装は最も軽い。しかし第二段階でログインを実装すると、**管理者が新しいパスワードを伝えてもそのユーザーはログインできない**。一覧の「ロック状態」列を見れば分かるが、完了ダイアログを閉じた直後の管理者がその列に目を向けるとは限らない。画面側で防げたのに防がなかった、という結果になる。

**共通ダイアログ — `showAlertDialog` に「赤くする一文」の引数を足す** — 既存の 19 か所を変えずに済む。しかし `message` の中から部分文字列を探して赤くする方式になるため、**後から文言を直したときに引数側を直し忘れると、エラーも出ないまま赤くならなくなる**。

**共通ダイアログ — `message` の型を `List<TextSpan>` に変える** — 自由度は高いが、色を変えない 19 か所すべてを書き換えることになり、文言が断片に分かれて読みにくくなる。

**検証エラー後 — 確認用だけが一致しないときはパスワード欄を残す** — 打ち直しが 1 欄で済む。しかし**打ち間違えたのがどちらの欄かは画面から判別できない**。パスワード欄を正しいものとして扱うと、確認用の欄が存在する目的（パスワード欄の打ち間違いを捕まえる）が無効になる。`Pa$$w0rd` のつもりで `Pa$$w0rf` と打ち、確認用は正しく打った場合、残った誤った値に合わせて打ち直すと**意図していないパスワードが確定する**。パスワードリセットでは「管理者が伝えたパスワードでログインできない」に直結する。

## 結果として生じること

- **この画面だけ、一覧への指示元がルートの `onExit` になる。** 画面は常に `context.pop()`（値なし）で閉じ、`onExit` が ViewModel の状態を読んで「1 行差し替え」「取り直し」「何もしない」の 1 つを選ぶ。`onExit` は「戻る」もブラウザの戻るボタンも通る唯一の場所であり、経路による漏れがない。代償として、一覧の再読み込みを起こす場所が一覧画面（他の操作）とルート（この画面）に分かれる。
- **`pop` の戻り値の型（`UserEditResult` 相当）を作らない。** 指示を `onExit` に寄せたため不要になり、結果として編集画面の型と形だけ同じものが 2 つ並ぶ事態も避けられた。
- **状態に「一覧への指示」を表す 2 つの値を持つ。** `updatedUser`（成功したときの更新後のユーザー）と `needsListReload`（404・成否不明）。**成功時に `needsListReload` を下ろす**ため、成否不明のあと押し直して成功した経路でも差し替えと取り直しが二重に走らない。
- **成否不明のあとも離脱確認が出る。** `isCompleted` を立てないため。パスワードは 2 欄に同じ値を打ち直す必要があり、誤って戻ると入力だけでなく「もう一度押せば決着する」という利点そのものを失う。
- **「実行する」は何回でも押せる。** 回数の制限は設けない。実行中はローダーが覆い、二重送信の同期ガードも効くため、通信が重なることはない。
- **完了ダイアログは、対象がロック中のときだけ 1 文増える。** 判定には**API が返した更新後のユーザー**の `isLocked` を使う（取得時の値ではない）。赤は既存の `0xFFD32F2F`（`FieldError` の背景・一覧の「削除」ボタンと同じ）で、白背景に対するコントラスト比は約 5.0:1 で WCAG AA を満たす。この画面の赤字は 1 文だけに絞っており、赤が出たら「通常とは違う状態が残っている」という 1 つの意味に固定される。
- **`showAlertDialog` が `showRichAlertDialog` の薄いラッパーになる。** ダイアログの体裁（外側タップで閉じない・OK だけ）は `showRichAlertDialog` が持ち、文字列版はそこへ委譲する。既存の 19 か所（一覧 6・編集 7・登録 4・ルート 2）は 1 行も変わらない。`showConfirmDialog` は赤字が不要なため手を入れていない。
- **検証エラーが出ると、この画面のフォームは必ず空になる。** 入力欄がパスワードの 2 欄だけで、その両方をクリアするためである。登録画面は 4 欄のうち 2 欄が残っていたが、規則（パスワード関連のエラーならパスワードの 2 欄をクリアする）は同じものを共有しており、**登録画面側には手を入れていない**。
- **ユーザー名とメールアドレスは 16px・黒で表示する。** 編集画面の「編集前の値」（14px グレー）とは体裁を分ける。あちらはすぐ下の入力欄に同じ値がある参照用だが、この画面では対応する入力欄がなく、これが唯一の表示であり、役目も「誰のパスワードを書き換えるのか」を示すことだからである。
- **入力欄には何も埋め込まない。** API は `password_hash` を返さないため、埋め込む値が存在しない。取得したユーザーは、この 2 行の表示とロック判定にのみ使う。
- **409 の分岐が存在しない。** メールアドレスを送らないため起きない。400 の `fields` に入るのも `password` の 1 項目だけである（確認用は API に送らない）。
