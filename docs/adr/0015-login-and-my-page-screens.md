# ログイン画面・マイページ・パスワード変更画面と、最終ログイン日時の記録

ステップ 2-3 の「ログイン画面とマイページを作成する」について、画面の構成と遷移、エラーの扱いを決めた。**マイページから離れること（「戻る」・ブラウザの戻る）はログアウトを伴い、パスワード変更はマイページのタイトルバーの「ユーザー名」ボタンのメニューから開く。** あわせて、ステップ 2-2 で漏れていた**最終ログイン日時を `users.last_login_at` に記録し、第一段階のユーザー一覧に表示する**（マイページには表示しない）。

API は [ADR 0012](0012-session-based-authentication.md)・[ADR 0013](0013-session-timeouts-and-user-crud-access.md)・[ADR 0014](0014-login-logout-api-spec.md) で決めたものをそのまま使う。画面の基本の動作・レイアウト・検証・エラーの振り分けは、第一段階の画面（[ADR 0008](0008-user-create-screen.md)・[ADR 0010](0010-user-password-reset-screen.md)）を踏襲する。以下は、踏襲**できなかった**点と、この段階で新たに決めた点を記録している。

## 決定した内容

### 画面と URL

| 画面 | URL | 開き方 | 開く操作 |
|---|---|---|---|
| ログイン画面 | `/login` | `go` | ホーム画面の「ユーザーログイン」、メニューの「ログアウト」の後 |
| マイページ | `/me` | `go` | ログインの成功 |
| パスワード変更画面 | `/me`（スタックで開き、マイページと同じ URL） | `push` | マイページのメニューの「パスワード変更」 |

- ユーザー一覧（`/users`）から `push` で開く画面と同じ形である（[ADR 0011](0011-user-delete-screen.md)）
- ログイン画面の「戻る」はホーム画面へ戻る。入力があっても離脱確認は出さない
- ログアウトの後やログイン状態が切れた後にアプリの中からログイン画面へ移る場合は、ログインしていたユーザーのメールアドレスを入力欄に入れておく。値はメモリにしかないため、ログイン画面で再読み込みすると消える

### ブラウザの履歴（スタックで開く画面すべて）

ユーザー一覧から開く画面（新規登録・編集・パスワードリセット・削除）と、マイページから開くパスワード変更画面に共通の決定である。

| 画面 | 押すボタン | 戻り先 |
|---|---|---|
| 新規登録・編集・パスワードリセット・削除 | 画面の「戻る」・ブラウザの戻る | ユーザー一覧 |
| ユーザー一覧（上記の画面を閉じた後） | ブラウザの戻る | ホーム |
| パスワード変更 | 画面の「戻る」・ブラウザの戻る | マイページ |
| マイページ（パスワード変更を閉じた後） | ブラウザの戻る | マイページのまま（戻り先のログイン画面で、ログイン状態のためマイページへ戻される） |

- スタックに画面を積むときは、ブラウザの履歴を 1 つ追加する。積んだ画面を閉じるときは、新しい記録を追加せず、ブラウザの履歴を 1 つ戻す（開いたときに追加した記録を取り消す）
- go_router は、積んだ画面を閉じたときも閉じた後の状態を新しい記録として追加するため、そのままでは閉じた後のブラウザの戻るで、閉じたはずの画面が再び表示される
- 判定は、ルーターが履歴を記録する箇所（`RouteInformationProvider`）の 1 か所で行う。「URL が同じで、積んだ画面の数が減った」記録が来たら履歴を 1 つ戻す。閉じる前に確認ダイアログを挟む画面でも、閉じた時点の記録で判定される

### タイトルバー

| 画面 | 左端 | 中央 | 右端 |
|---|---|---|---|
| ログイン画面 | 「戻る」（ホーム画面へ） | ユーザーログイン | なし |
| マイページ | 「戻る」（ログアウトの確認を出す） | マイページ | 「ユーザー名」ボタン（メニュー：「パスワード変更」「ログアウト」） |
| パスワード変更画面 | 「戻る」（マイページへ） | パスワード変更 | 「ユーザー名」ボタン（メニュー：「ログアウト」のみ） |

- 「ユーザー名」ボタンは、ユーザー名の長さに応じて幅が広がり、最大 240px で末尾を省略する。「戻る」ボタンがコンテンツ幅の左端に揃うのと同じく、コンテンツ幅の右端に揃える

### ログアウトと遷移先

| 操作 | 確認ダイアログの「はい」の後 |
|---|---|
| メニューの「ログアウト」（マイページ・パスワード変更画面） | ログアウトしてログイン画面へ |
| マイページの「戻る」・ブラウザの戻る | ログアウトしてホーム画面へ |

- 確認ダイアログの「いいえ」では、何もせず元の画面に留まる
- ログアウトでサーバーに接続できなかった場合や、その他の失敗（401 を除く）の場合は、アラート「ログアウトできませんでした」を出し、元の画面に留まる

### ログイン状態の判定

| 場面 | 扱い |
|---|---|
| 画面を開いたとき（マイページ・パスワード変更画面）に、ログイン状態にない | ダイアログを出さずにログイン画面へ移る |
| 画面の操作（パスワード変更・ログアウト）で、API が 401 `unauthenticated` を返した | アラート「ログイン状態が切れました。もう一度ログインしてください。」→「OK」でログイン画面へ移る |
| ログイン状態のままログイン画面を開いた | ダイアログを出さずにマイページへ移る（`GET /api/me` で確かめる） |
| マイページを開いたときに、`GET /api/me` が 401 以外で失敗した | アラート「取得に失敗しました」（2 行目は「しばらく待ってから、画面を開き直してください。」）→「OK」でホーム画面へ移る |

### マイページ

- コンテンツ部分には、ユーザー名とメールアドレスだけを表示する。表示の形はパスワードリセット画面のユーザー名・メールアドレスと同じ（ADR 0010）

### パスワード変更画面

- 案内文、「現在のパスワード」「新しいパスワード」「新しいパスワード（確認用）」の 3 欄、「パスワードを表示する」（3 欄をまとめて切り替える）、「変更する」ボタン
- ユーザー名とメールアドレスは表示しない（タイトルバーの「ユーザー名」ボタンで分かり、ログインしている本人が操作しているため）
- 入力があるときに離れようとすると、「入力内容を破棄します」の確認を出す

| 結果 | 扱い |
|---|---|
| 成功 | 「パスワードを変更しました」／「次回のログインから新しいパスワードを使用してください。\nほかの端末やブラウザでログインしていた場合は、\nログアウトされました。」→「OK」でマイページへ |
| 入力エラー | 各入力欄の直下に表示する。エラーが出た欄の組だけをクリアする（下記） |
| 403 `account_locked` | 「パスワードを変更できませんでした」＋ API の文言 →「OK」でログイン画面へ |
| サーバーに接続できない（成否不明） | 「パスワードを変更できたか確認できませんでした」／「サーバーに接続できませんでした。\nもう一度「変更する」を押してください。\n「現在のパスワードが正しくありません」と表示された場合は、すでに新しいパスワードに変更されています。」。画面に留まり、入力を残す |
| その他（500、403 `csrf_token_invalid` など） | 「パスワードを変更できませんでした」＋ API の文言。画面に留まり、入力を残す |

**入力エラーのときにクリアする欄**

| エラーが出た欄 | クリアする欄 |
|---|---|
| 現在のパスワード | 現在のパスワード |
| 新しいパスワード・確認用のいずれか | 新しいパスワード・確認用 |
| 両方 | 3 欄すべて |

### ログイン画面のエラー

- 入力の検証は「空かどうか」だけ（ADR 0014）。空の欄は、欄の直下に「メールアドレスを入力してください」「パスワードを入力してください」を表示する
- 認証に関するエラーは、タイトル「ログインできませんでした」のアラートダイアログで表示する

| 場面 | メッセージ | 入力欄 |
|---|---|---|
| 401 `invalid_credentials` | API の文言 | パスワードだけをクリアする |
| 403 `account_locked` | API の文言 | 変えない |
| 429 `too_many_requests` | nginx の文言 | 変えない |
| 403 `csrf_token_invalid` | API の文言 | 変えない |
| サーバーに接続できない | 「サーバーに接続できませんでした。\nもう一度お試しください。」 | 変えない |
| その他 | API の文言 | 変えない |

### 最終ログイン日時

| 項目 | 内容 |
|---|---|
| 記録する場所 | `users.last_login_at`（`TIMESTAMPTZ`、NULL を許可）。一度もログインしていないユーザーは NULL |
| 更新する時点 | ログインに成功したとき（Web・モバイルの両方） |
| 更新しない時点 | ログインの失敗、ログアウト、パスワード変更、管理者による操作 |
| `updated_at` | 変えない（ADR 0014 で失敗の回数の加算・0 に戻すときに変えないと決めたのと同じ） |
| API | 管理者向けのユーザー API のレスポンスに `last_login_at` を追加する。`GET /api/me` には追加しない |
| 画面 | ユーザー一覧のテーブルの右端（「ログイン失敗回数」の右）に「最終ログイン日時」列を追加する。マイページには表示しない |

## 検討した選択肢

**マイページの「戻る」 — ログアウトせずにホーム画面へ戻る** — ホーム画面の API 疎通テストやユーザー管理へ、ログインしたまま移れる。しかしマイページはログインした利用者のための画面であり、そこから離れた後もログイン状態が残ると、ホーム画面を見ている利用者がログアウトしたと思い込んだまま、ブラウザに有効なセッションが残る。離れることをログアウトと結び付け、確認ダイアログで意図を確かめる形とした。

**マイページの取得失敗 — マイページに留まる** — ログアウトせずにホーム画面へ移る経路を作らずに済む。しかし、ユーザー名が分からないまま空のマイページを見せることになる。セッションが残っていれば、開き直したときに「ログイン状態のままログイン画面を開いたらマイページへ移る」規則でマイページが表示されるため、ホーム画面へ戻しても利用者が困ることはない。

**パスワード変更の成否不明 — パスワードリセット画面と同じく「もう一度お試しください」とだけ案内する** — ADR 0010 は「同じパスワードで上書きし直しても結果が同じ（冪等）」ことを理由に押し直しを促した。本人によるパスワード変更は、現在のパスワードとの照合を伴うため冪等ではない。実際には変更が成功していた場合、押し直すと古いパスワードを現在のパスワードとして送ることになり、API は「現在のパスワードが正しくありません」を返して失敗の回数を 1 加算する。この結果の意味をダイアログで先に伝え、押し直しの結果で利用者が成否を判別できるようにした。加算は 1 回だけで、次に照合に成功すれば 0 に戻る。

**403 `account_locked`（パスワード変更） — 画面側でロックのきっかけを判別する** — 今回の失敗でロックされた場合は API がセッションを削除し、別の端末のログインの失敗ですでにロックされていた場合はセッションが残る（ADR 0014）。レスポンスは同じで、画面からは区別できない。「OK」でログイン画面へ移すと決めておけば、前者ではログイン画面が表示され、後者では「ログイン状態のままログイン画面を開いたらマイページへ移る」規則でマイページが表示される。判定を画面に持たずに、それぞれの状態に合った画面へ移る。

**入力エラーのクリア — 常に 3 欄すべてをクリアする（既存の規則をそのまま当てはめる）** — 既存の画面は、パスワードに関する入力エラーでパスワードの 2 欄をクリアしている（ADR 0010）。その理由は「検証を通らなかった値を伏せ字の裏に残さない」ことと「確認用だけが一致しない場合、打ち間違えたのがどちらの欄か判別できない」ことで、どちらも欄の組の単位で成り立つ。3 欄すべてをクリアすると、現在のパスワードだけを打ち間違えた場合に、正しく入力できていた新しいパスワードの 2 欄まで打ち直させることになる。

**ログインの 429 — 認証の失敗（401）と同じく、パスワードをクリアする** — ADR 0014 のとおり、nginx の呼び出し回数の制限は同じ IP アドレスを共有する利用者の呼び出しを合わせて数えるため、正しいメールアドレスとパスワードを入力した利用者も、他人の呼び出しのあおりで拒否される。429 は入力の誤りではなく、入力をクリアすると、正しい入力を打ち直させることになる。

**パスワード変更画面 — `go` で開き、`/me/password` を URL に出す** — 再読み込みしてもパスワード変更画面が表示される。しかしパスワード変更画面はマイページのメニューから開く画面で、URL を単独で使う場面がなく、ADR 0011 で削除画面を `push` とした理由がそのまま当てはまる。

**最終ログイン日時 — 前回のログイン日時をマイページに表示する** — 今回のログイン日時を表示すると、ログインした直後のマイページには常にほぼ現在の日時が表示され、利用者が得る情報がない。前回のログイン日時を表示すれば、覚えのない日時から他人のログインに気付けるが、前回の値を別に持つ仕組みが必要になる。マイページには表示せず、管理者がユーザー一覧で確認できるようにした。

## 結果として生じること

- **ADR 0002 の `users` テーブルに `last_login_at` の列が加わる。** マイグレーション `000005` で追加する。
- **ADR 0004 のユーザー API のレスポンスが 10 項目になる。** `last_login_at` は一度もログインしていないユーザーでは `null` である。
- **ログインに成功すると、`failed_login_attempts` を 0 に戻すのと同じ 1 つの `UPDATE` で `last_login_at` を更新する。** 失敗の回数が 0 のときも、最終ログイン日時を更新するため `UPDATE` を実行する。
- **ユーザー一覧のテーブルは、1,366px の画面で全列が収まらなくなる。** 既存の仕組みのとおり、テーブルの中に横スクロールが出る。
- **Web アプリは、手元の CSRF トークンを失ったら `GET /api/csrf-token` で取り直す（ADR 0012）。** ログインの成功・ログアウトの成功・403 `csrf_token_invalid` のときに手元のトークンを破棄し、次の送信の前に取り直す。ログイン前のトークンは、ログインの後には使えないためである。
- **マイページとパスワード変更画面の離脱確認は、プログラムから画面を移すとき（ログアウトの成功・401・ロック・取得の失敗）には出さない。** 確認を出してよい状態かを、ログイン中のユーザーを持つ状態に記録してから画面を移す。
- **マイページの「戻る」とブラウザの戻るは、どちらもルートの `onExit` を通る。** ブラウザの戻るの行き先がホーム画面以外であっても、ログアウトの後はホーム画面へ移す。
