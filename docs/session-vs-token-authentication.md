# セッション方式とトークン方式の違い

ログイン状態の管理方式である「セッション方式」と「トークン方式（JWT など）」について、仕組みと、場面ごとにどちらが有利になるかをまとめたものです。

## 0. 前提知識：REST

**REST** は、Web API の設計で最も普及している考え方です。データを「リソース」として URL で表し、`GET`（取得）/ `POST`（作成）/ `PUT`（更新）/ `DELETE`（削除）の HTTP メソッドで操作します。例えば `GET /api/users/1` は「ID が 1 のユーザーを取得する」という意味になります。仕組みが単純で、ブラウザや既存のツールでそのまま扱えるのが特徴です。

### ステートレスという原則

REST には「サーバーはリクエストとリクエストの間でクライアントの状態を覚えておかず、各リクエストが処理に必要な情報をすべて持っている」という原則（**ステートレス**）があります。

この原則の目的は、「どのサーバーでも同じリクエストを処理できるようにして、サーバーを増やしやすくすること」です。

### セッション方式・トークン方式との関係

**どちらの方式を選んでも、REST API を作って運用する上での有利・不利は生じません。ただし、REST の設計思想（ステートレス）を忠実に守れるのはトークン方式です。**

- **トークン方式**：リクエストに付いたトークン自体にユーザー情報が入っており、サーバーはログイン状態を覚えておく必要がない。原則に忠実。「REST なら JWT」と言われるのはこのため
- **セッション方式**：ログイン状態をサーバー側に持つため、厳密に解釈すると原則から外れる。ただし、セッションを API サーバーのメモリではなく共通の DB に置けば、どのサーバーでも同じリクエストを処理できるため、原則の目的は満たせる

有利・不利が生じない理由は、URL の設計、HTTP メソッドの使い分け、ステータスコードの返し方といった REST API の設計が、どちらの方式でも変わらないためです。違いは「リクエストに付いてきた文字列から、どうやって本人を特定するか」という、API の入り口の処理だけです。実際に、公開されている REST API でも、意味を持たないランダムな文字列をアクセストークンとして発行し、サーバー側の記録と照合する形（仕組みとしてはセッション方式と同じ）は広く使われています。

## 1. 2 つの方式の仕組み

| 方式 | ログイン成功時にサーバーがすること | 以降のリクエストでサーバーがすること | ログイン状態の実体 |
|---|---|---|---|
| セッション方式 | 「誰がログイン中か」の記録を DB に保存し、その記録の番号（**セッション ID**）をクライアントに渡す | 送られてきたセッション ID で DB を引き、本人を特定する | **サーバー側**（DB の記録） |
| トークン方式 | ユーザー ID や有効期限を詰め込み、改ざん防止の署名を付けた文字列（**トークン**）をクライアントに渡す。DB には何も書き込まない | 署名が正しいことと有効期限内であることだけを確認し、中身からユーザー ID を読み取る | **クライアント側**（トークンそのもの） |

この「ログイン状態の実体がどちらにあるか」の違いが、以降のすべての差の元になります。

## 2. 複数の端末から同時にログインした場合

どちらの方式でも、端末（正確にはブラウザやアプリ）ごとに別々のセッション ID / トークンが発行され、それぞれがそれで接続します。同じ PC でも、Chrome と Safari なら別々になります。

| | セッション方式 | トークン方式 |
|---|---|---|
| サーバーの記録 | ログインした端末の数だけ、セッションの記録が DB に並ぶ | 何も残らない。**何台でログインしているかをサーバーは把握していない** |
| PC-A でログアウトしたとき | PC-A のセッションの記録を DB から削除する。その ID は以降使えない | PC-A がトークンを捨てるだけ。**サーバー側では何も起きず、トークン自体は有効期限まで有効なまま**。事前に盗まれていれば、盗んだ側は期限まで使える |
| PC-B への影響 | なし（ログインしたまま） | なし（ログインしたまま） |

## 3. 1 人 1 端末に制限する（排他制御）場合

排他制御には 2 通りのやり方があります。

- **後勝ち**：新しい端末でログインしたら、古い端末を強制的にログアウトさせる
- **先勝ち**：すでにログイン中なら、別の端末からのログインを拒否する（ログアウトせずにブラウザを閉じると、有効期限が切れるまで誰もログインできなくなる点に注意）

**セッション方式が有利です。** 排他制御には「サーバーが、そのユーザーの現在のログインを把握していること」が必要で、セッション方式は最初からそれを持っているためです。

- **セッション方式**：DB の操作だけで実現できる。後勝ちなら、ログイン時にそのユーザーの既存のセッションを削除してから新しいセッションを作る。先勝ちなら、既存のセッションが残っていればログインを拒否する
- **トークン方式**：そのままでは実現できない。「このユーザーの有効なトークンはこれだけ」という記録を DB に持たせ、リクエストのたびに照合する処理を足せば実現できる。ただしこれはセッション方式とほぼ同じ仕組みであり、トークン方式の利点である「DB を引かずに本人を確認できる」が失われ、署名の検証と DB の照合を二重に行うことになる

## 4. モバイルアプリ（スマホ・タブレット）も同じ API を使う場合

一般に「モバイルならトークン方式」と言われますが、実際には次の 2 つの軸がまとめて語られています。

| 軸 | 選択肢 | モバイルへの影響 |
|---|---|---|
| ① ログイン情報の送り方 | Cookie / `Authorization` ヘッダー | **ヘッダーが有利** |
| ② ログイン状態の持ち場所 | サーバーの DB（セッション方式） / トークン自体（JWT） | 影響しない |

**① がモバイルで差になる理由**：Cookie は**ブラウザの仕組み**で、ブラウザは受け取った Cookie を自動で保存し、次のリクエストに自動で付ける。モバイルアプリの HTTP 通信にはこの自動処理がないため、アプリ側で作り込む必要がある。ヘッダー方式では、アプリがログイン時に受け取った文字列を端末の安全な保管場所（iOS の Keychain、Android の Keystore）に保存し、リクエストごとに `Authorization: Bearer <文字列>` として付ける。モバイルアプリでは標準的なやり方で、無理がない。

**② が影響しない理由**：ヘッダーで送る文字列は JWT でなくてもよい。セッション ID をそのままヘッダーで送れば、サーバーは Cookie の場合と同じように DB を引いて本人を特定できる。この場合も、排他制御や強制ログアウトのしやすさはそのまま残る。

### Web もヘッダーに統一できるか

できます。Web でもログイン時に受け取ったセッション ID をブラウザ内に保存し、リクエストのたびに `Authorization` ヘッダーへ付けて送れば、Web とモバイルを同じ仕組みにそろえられます。ただし、Web では推奨されません。

**メリット**

| メリット | 何が起きるか | どうしてそうなるか |
|---|---|---|
| ① 仕組みが 1 本になる | ログイン API は常に本文でセッション ID を返し、ミドルウェアもヘッダーだけを読めばよい | 送り方が Web とモバイルで同じになるため |
| ② CSRF 対策がいらない | 罠サイトに仕込まれた「勝手に送信するフォーム」から API を呼ばれても、ログイン中として扱われない | Cookie はブラウザが**自動で**付けるため、罠サイトからのリクエストにも付いてしまう（これが CSRF）。ヘッダーはアプリのコードが明示的に付けない限り送られないため、罠サイトからのリクエストには付かない |

**デメリット**

| デメリット | 何が起きるか | どうしてそうなるか |
|---|---|---|
| ① XSS で盗まれる | 悪意のあるスクリプトを画面に埋め込まれると、セッション ID を読み取られて外部に送られる。攻撃者は自分の PC から、そのセッションが消されるまでなりすましを続けられる | ヘッダーに付けるには JavaScript（Flutter のコード）から読める場所に保存する必要があり、読める場所は攻撃スクリプトからも読めるため。HttpOnly 属性付きの Cookie なら、スクリプトからは読めない |
| ② 保存場所の選択で使い勝手が変わる | 盗まれにくいメモリ上に置くと、画面を再読み込みするたびにログアウトされる。再読み込みしてもログインが残る localStorage に置くと、①の危険をそのまま抱える | 盗まれにくさとログインの残りやすさが両立しないため |
| ③ 送信処理を自分で作る | 保存・読み出し・全リクエストへの付与を Flutter 側で実装し、付け忘れがないようにする必要がある | Cookie と違い、ブラウザが自動でやってくれないため |

Cookie で送る場合は、代わりに CSRF 対策が必要になります。ただし、Cookie に `SameSite` 属性を付けると「別のサイトから送られたリクエストには Cookie を付けない」とブラウザに指示でき、画面と API が同じドメインの構成なら、これでほぼ防げます。一方、ヘッダーに統一した場合の XSS による盗難は、ブラウザの設定では防げません。このため、**Web ではセッション ID を HttpOnly 属性付きの Cookie で送るのが一般的な推奨**となっており、OWASP（Web セキュリティの代表的な指針をまとめている団体）も、セッション ID を localStorage に保存しないよう勧めています。

### モバイルでヘッダーを使っても、上記のデメリットが生じない理由

根本的な違いは、**ブラウザは「外から届いたコードを実行する環境」、モバイルアプリは「インストール時に組み込まれたコードだけを実行する環境」**だという点です。

| デメリット | Web で起きる理由 | モバイルで起きない理由 |
|---|---|---|
| ① XSS で盗まれる | ブラウザは、サーバーから届いた HTML や JavaScript をその場で実行する。紛れ込んだスクリプトを正規のコードと区別できず、アプリと同じ権限で実行してしまう | ネイティブアプリのコードは、ビルド時に組み込まれたものだけ。API から届いたデータは「表示する文字」として扱われ、コードとして実行されない。スクリプトを紛れ込ませる入り口がない |
| ② 保存場所の選択で使い勝手が変わる | ブラウザには「アプリのコードからは読めて、ページを閉じても残り、しかも紛れ込んだスクリプトからは読めない」保存場所がない | Keychain（iOS）/ Keystore（Android）は、アプリを閉じても残り、OS がアプリごとに鍵をかけて守っているため他のアプリからは読めない。盗まれにくさとログインの残りやすさを両立できる |
| ③ 送信処理を自分で作る | Cookie ならブラウザが自動でやってくれるのに、ヘッダーにしたせいで手間が増える | モバイルでも実装は必要。ただしモバイルアプリには Cookie を自動で扱うブラウザの仕組みがないため、Cookie を選んでも同じ手間がかかり、差にならない |

**例外**

- アプリの中で Web ページを表示する部品（WebView）を使い、そこで JavaScript を動かしている場合は、その部分に限って XSS が起こりえる
- 脱獄や root 化で OS の保護を外した端末では、Keychain / Keystore の保護が効かなくなる（次項）

### 脱獄・root 化された端末について

**トークン方式でも防げません。** モバイルアプリでは、トークンもセッション ID と同じく Keychain / Keystore に保存するため、OS の保護が外れればどちらも同じように読み取られます。これは「端末の中に保存したログイン情報をどう守るか」という問題で、ログイン状態をサーバーに持つかトークンに持たせるかとは関係がありません。盗まれた後は、サーバーからセッションを削除すればすぐに無効にできるセッション方式の方が有利です（5 章）。

脱獄や root 化は、基本的に**端末の持ち主が自分で行う**ものです。そのため、被害の範囲は次のように限られます。

| 状況 | 何が起きるか | 影響の範囲 |
|---|---|---|
| 持ち主が自分で脱獄し、自分のセッション ID を読む | 自分のログイン情報を自分で見るだけ | 被害なし（もともとそのユーザー本人のため） |
| 持ち主が脱獄した端末に、悪意のあるアプリが入り込む | そのアプリにセッション ID を盗まれる | **その端末の持ち主のアカウントだけ**。保護を外したのが持ち主自身のため、他の利用者には広がらない |
| 他人が端末を盗み、脱獄して読み取ろうとする | 現在の iOS / Android では、画面ロックがかかった端末を他人が脱獄するのは非常に難しい。Keychain / Keystore の中身は、画面ロックの解除に使う情報と結びついて暗号化されている | 画面ロックを設定していれば、現実的な脅威になりにくい |

この問題はモバイルに限りません。PC にマルウェアが入り込めば、ブラウザが保存している Cookie も同じように読み取られます。**端末そのものを乗っ取られた場合は、どの方式でもログイン情報を守りきれない**、というのが前提です。そのうえで被害を小さくするには、「盗まれたと分かったら、サーバー側ですぐに無効にできる」ことが効いてきます。

### API を Web アプリとモバイルアプリで共通して利用する場合

**Cookie とヘッダーの両方で受け付け、Web は Cookie、モバイルはヘッダーで送らせる**のが推奨です。それぞれの環境で最も安全な送り方が異なるためです。

| クライアント | 送り方 | 理由 |
|---|---|---|
| Web | HttpOnly 属性付きの Cookie | ブラウザには XSS の危険があり、スクリプトから読めない保存場所は HttpOnly の Cookie しかない。CSRF の対策は必要になる（6 章） |
| モバイル | `Authorization` ヘッダー | XSS の入り口がなく、Keychain / Keystore という安全で消えない保存場所がある。Cookie を自動で扱う仕組みもない |

どちらの送り方でも、サーバーは同じ DB のセッションを引いて本人を特定します。違うのは入り口の読み取りだけで、強制ログアウトや排他制御などのセッション方式の利点は、Web とモバイルの両方で同じように使えます。

**留意しておくべきこと**

- **Web にはセッション ID をレスポンスの本文で返さない**：本文に含めると、Flutter のコード（JavaScript）から読める状態になり、HttpOnly の Cookie で守っている意味がなくなる。セッション ID を本文で返すのはモバイルからのログインに限り、Web には Cookie だけで渡す
- **Web とモバイルの見分け方を明確に決めておく**：見分けを誤ると、上記の「Web に本文で返してしまう」事故につながる。例えば、ログイン API のパスを Web 用とモバイル用で分けるなど、取り違えようのない形にする
- **モバイルアプリがまだない間は、ヘッダーの経路を実際のアプリで確かめられない**：テストコードでは確認できるが、実際には使われない経路を保守し続けることになる

**運用やその他のコスト**

Cookie だけで受け付ける場合と比べて、コストは大きくなりません。増えるのは API の入り口の処理だけで、セッションを DB で管理する中心部分は同じです。

| 対象 | 増える作業 | 規模 |
|---|---|---|
| ログイン API | Web からのログインかモバイルからのログインかを見分け、Web には Cookie で、モバイルには本文でセッション ID を返し分ける | 小。分岐が 1 か所増える |
| ミドルウェア | Cookie を読み、なければ `Authorization` ヘッダーを読む | 小。数行 |
| ログアウト API | ミドルウェアと同じく、どちらからでも読めるようにする | 小。ミドルウェアの読み取りを使い回せる |
| セッションのテーブル（DB） | 変わらない | なし |
| Web アプリ | 変わらない | なし |
| テスト | 入り口のテストが Cookie とヘッダーの 2 通りになる | 小〜中。入り口の部分だけ 2 倍になる |
| 運用（サーバー・インフラ） | 変わらない | なし |

モバイルアプリ側の「Keychain / Keystore への保存」と「ヘッダーへの付与」は、モバイルアプリを作る以上どちらを選んでも必要になるため、この選択による追加コストには含めていません。コードの量よりも、上記の「留意しておくべきこと」を守り続けることがコストの中心になります。

## 5. セッション ID / トークンを盗まれたり改ざんされたりした場合

**盗まれた場合は、なりすましされます。** これは Cookie で送る場合も、ヘッダーで送る場合も、JWT の場合も同じです。どれも「持っている人を本人とみなす」仕組みのため、この弱点はどの方式にもあります。対策は「盗ませないこと」と「盗まれたときの被害を小さくすること」の 2 つです。

**改ざんによるなりすましは、事実上できません。** セッション ID は、意味を持たない長いランダムな文字列（例：128 ビット以上の乱数）です。一部を書き換えても、別の人の有効な ID に当たる確率は極めて低く、書き換えた ID は DB に記録がないため未ログインとして扱われます。JWT は、書き換えると署名が合わなくなるため受け付けられません。

**盗まれる経路と対策**

| 経路 | 何が起きるか | 対策 |
|---|---|---|
| 通信の途中で盗み見る | 通信を傍受して ID を読み取る | HTTPS で通信を暗号化する |
| 端末の中から盗み出す（モバイル） | 保存場所から他のアプリが読み取る | Keychain / Keystore に保存する。OS が保護しており、他のアプリからは読めない |
| 端末の中から盗み出す（Web） | 悪意のあるスクリプトを画面に埋め込まれ（XSS）、ID を読み取られる | Web はヘッダーではなく **HttpOnly 属性付きの Cookie** で送る。この Cookie は JavaScript から読めないため、スクリプトでは盗めない |
| サーバーの DB から漏れる | DB の中身が流出し、そのまま使われる | DB には ID そのものではなくハッシュ値を保存する（パスワードと同じ考え方） |

**盗まれたときの被害の抑え方**：ここはセッション方式が有利です。DB から該当するセッションを削除すれば、盗まれた ID はその時点で使えなくなります。JWT は有効期限までは止められません。

## 6. CSRF への対策

### CSRF とは

**CSRF** は、罠サイトが、ログイン中の利用者のブラウザに、本人の意図しないリクエスト（パスワードの変更、データの削除など）を送らせる攻撃です。ブラウザは Cookie を自動で付けるため、何も対策しなければ、サーバーは本人の操作として処理してしまいます。

- **成立するのは、Cookie でログインを確認するリクエストだけ**：モバイルアプリのようにセッション ID を `Authorization` ヘッダーで送る場合、ヘッダーはアプリのコードが明示的に付けない限り送られず、罠サイトのコードがアプリの中で動くこともないため、CSRF は成立しない。ただし、モバイルアプリの中で WebView を使い、その中で Cookie によるログインを使う場合は、ブラウザと同じ状況になる
- **ログイン CSRF**：罠サイトが利用者のブラウザを、**攻撃者のアカウントで**ログインさせる攻撃。利用者は気付かずに攻撃者のアカウントで操作し、入力した情報が攻撃者に見られてしまう。利用者の Cookie を使わない攻撃のため、Cookie の `SameSite` 属性では防げない

### 対策のセオリー

**「データを変更する操作は `GET` で行わない」を前提に、基本の対策を 1 つ置き、補強の対策を重ねる（多層防御）**のがセオリーです。1 つの対策に頼らないのは、実装の入れ忘れやブラウザの仕様の違いで、どれか 1 つが効かない場面が起こりうるためです。

- **前提（`GET` でデータを変更しない）**：どの対策も `POST` / `PUT` / `DELETE` を守る仕組み。`GET` でデータを変更すると、リンクを踏ませるだけで操作が成立してしまい、対策の外に穴ができる。一方、`GET` がデータを変更しなければ、罠サイトから送らせても何も変わらず、ブラウザの「別のサイトの画面の中身は読めない」という決まり（同一オリジンポリシー）により、罠サイトは結果を読み取ることもできない

| 対策 | 位置づけ（OWASP） | 内容 | 何に頼って守るか |
|---|---|---|---|
| CSRF トークン | **基本の対策** | サーバーが推測できないランダムな値を発行してセッションと結びつけ、データを変更するリクエストのたびにヘッダー（例：`X-CSRF-Token`）で送らせて照合する | 罠サイトがその値を知りようがないこと（同一オリジンポリシー） |
| Cookie の `SameSite` 属性 | 補強 | 別のサイトから送られたリクエストには Cookie を付けないよう、ブラウザに指示する | ブラウザが指示どおりに動くこと |
| `Origin` の判定 | 補強 | ブラウザが自動で付ける「どのサイトの画面から送ったか」を示すヘッダーを確認し、自分のドメイン以外なら拒否する | ブラウザが `Origin` を正しく付けること（JavaScript からは書き換えられない） |
| `Sec-Fetch-Site` の判定 | 補強 | ブラウザが自動で付ける「同じサイトからか、別のサイトからか」を示すヘッダーを確認し、別のサイトからなら拒否する | ブラウザがヘッダーを正しく付けること（JavaScript からは書き換えられない） |
| `Content-Type: application/json` だけを受け付ける | 補強 | JSON 形式以外のリクエストを拒否する | HTML フォームは JSON 形式で送れず、JavaScript で別のサイトへ JSON を送ろうとすると、ブラウザが事前にサーバーへ許可を確認し、許可がなければ送信しないこと |
| 重要な操作での再確認 | 補強 | パスワード変更などでは、現在のパスワードの入力を求める | 攻撃者がパスワードを知らないこと |

**最近の流れ**：現在の主要なブラウザはすべて `Sec-Fetch-Site` を付けるようになり、**`Sec-Fetch-Site` と `Origin` による判定を、トークンに代わる基本の対策とする考え方が広がっています。** Go も 1.25 から、この判定を行う `http.CrossOriginProtection` を標準ライブラリに含めています。

### CSRF トークンと `Origin` の判定の比較

**セキュリティの強固さ、セオリーの両面で、CSRF トークンの方が上です。**

| | CSRF トークン | `Origin` の判定 |
|---|---|---|
| セオリー上の位置づけ | 基本の対策 | 補強の対策 |
| 何に頼って守るか | サーバーが発行した値を、罠サイトが知りようがないこと | ブラウザが `Origin` を正しく付けること |
| 弱くなる場面 | ほぼない | 古いブラウザや一部のプライバシー保護の拡張機能・社内のプロキシなどで `Origin` が付かない、または `null` になる場合がある。「ヘッダーがなければ拒否」にすると正規の利用者まで弾き、「許可」にすると穴になる |
| ログイン API での利用 | そのままでは使えない（下記） | そのまま使える |
| 実装の手間 | サーバーで発行・保存・照合が必要。Web アプリ側も、トークンを受け取ってデータを変更するリクエストすべてに付ける必要がある | サーバー側の数行だけ。Web アプリ側の変更はなし |

現在の主要なブラウザは `Origin` を正しく付けるため、実用上の差は小さくなっています。それでも、ブラウザの実装に頼らずサーバー側だけで守りを完結できる CSRF トークンの方が、確実性は高いです。

**どちらも XSS には無力です。** 画面に紛れ込んだスクリプトは正規の画面と同じ場所から動くため、CSRF トークンも読めますし、`Origin` も正しい値になります。

### ログイン API の CSRF 対策

CSRF トークンは、発行した値を**セッションと結びつけて**照合する仕組みです。ログイン API を呼ぶ時点ではまだセッションがないため、**そのままでは使えません。** ログイン API で使える対策は次のとおりです。

| 対策 | 内容 |
|---|---|
| **ログイン前用の仮のセッションと CSRF トークン** | ログイン画面を開いた時点で仮のセッションを作り、そこに CSRF トークンを結びつける。ログインに成功したら、仮のセッションを捨てて正式なセッションと新しい CSRF トークンを作り直す。**OWASP がログイン CSRF の対策として挙げている方法で、セオリーどおりかつ最も強固**。ただし、ログイン前にもセッションを管理する必要があり、仕組みが大きくなる |
| `Origin` の判定 | セッションを必要としないため、そのまま使える |
| `Sec-Fetch-Site` の判定 | 同上 |
| `Content-Type: application/json` だけを受け付ける | 同上 |

セオリーどおりで最も強固な形は、**仮のセッションと CSRF トークンを基本の対策とし、`Origin` の判定を補強として重ねる**形です。

仮のセッションを使う場合、ログインに成功したら必ず正式なセッションと新しい CSRF トークンを発行し直します。仮のセッションのトークンを使い続けると、ログイン前に漏れたトークンがログイン後も使えてしまうためです。

### `Origin` の判定は YAGNI ではないか

**YAGNI には当たらず、セオリーの範囲内の対策です。ただし、正確には「必須」ではなく「推奨」の位置づけです。**

- **YAGNI に当たらない理由**：YAGNI は「今は必要ないのに、将来使うかもしれないと見越して作る」ことを避ける考え方。`Origin` の判定は将来のための機能ではなく、**今すでに存在する CSRF という攻撃**への対策のため、対象にならない
- **セオリーとしての位置づけ**：OWASP の CSRF 対策の指針は、CSRF トークンを基本の対策としたうえで、多層防御として追加で**検討すべき**対策に `Origin` の確認を挙げている。「入れなければ誤り」ではなく「重ねることが推奨される」対策
- **もう 1 つの役割（Web とモバイルが API を共通利用する場合）**：ブラウザは `POST` などに `Origin` を自動で付け、モバイルアプリの HTTP 通信は付けない。そのため Web 用のログイン API で `Origin` を判定すると、モバイルアプリが誤って Web 用のパスを呼んだとき、その場で 403 エラーとして弾ける。判定しない場合、ログインは成功するのにセッション ID を受け取れず（Cookie でしか返らないため）、その後の API がすべて 401 になるという、原因の分かりにくい失敗の仕方になる。ただし、意図的に `Origin` を付けたリクエストは通るため、これは「うっかり間違えた呼び出し」を弾くためのもの

| API | `Origin` の判定の役割 | 必要性 |
|---|---|---|
| Web 用のログイン API | ログイン CSRF への多層防御に加え、モバイルアプリからの誤った呼び出しを弾く | 高い。後者はトークンでは代わりにならない |
| ログイン後の、データを変更する API | CSRF トークンの不具合や入れ忘れに備える多層防御 | 推奨。トークンだけでも CSRF は防げる |

`Origin` の判定が防げないのは、`curl` などブラウザ以外の道具から `Origin` を付けて直接送られたリクエストです。ただしこの場合の攻撃者は自分で直接 API を呼んでいるだけで、利用者のブラウザを悪用しているわけではありません。正しいパスワードがなければログインできないため、パスワードの照合とアカウントロックが守りになります。

### API ごとの対策の割り当て（Web とモバイルが API を共通利用する場合）

セオリーどおりで最も強固な形にした場合の割り当てです（パスは例）。

| API の種類 | 例 | Web（Cookie） | モバイル（ヘッダー） |
|---|---|---|---|
| Web 用のログイン API | `POST /api/login` | **仮のセッションの CSRF トークン ＋ `Origin` の判定** | 使わない（呼ぶと `Origin` の判定で 403） |
| モバイル用のログイン API | `POST /api/mobile/login` | 使わない | なし |
| 仮のセッションと CSRF トークンを発行する API | ログイン画面を開いたときに呼ぶ | なし | 使わない |
| ログイン後の、データを変更する API（`POST` / `PUT` / `DELETE`） | `POST /api/logout`、`PUT /api/me/password` など | **CSRF トークン ＋ `Origin` の判定** | なし |
| ログイン後の、データを取得する API（`GET`） | `GET /api/me` など | なし | なし |

- **モバイルは全行「なし」**：CSRF が成立しないため
- **発行 API は「なし」**：罠サイトから呼ばせても、罠サイトは結果（トークン）を読めず、利用者のログイン状態も変わらないため
- **`GET` は「なし」**：データを変更しないため CSRF の被害がなく、罠サイトは結果も読めない。また、ブラウザは同じドメインへの `GET` に `Origin` を付けないため、判定を入れると Web アプリ自身が弾かれる
- **CSRF トークンの判定は、Cookie でログインを確認したリクエストだけに行う**：モバイルアプリのリクエストにまでトークンを求めると、モバイルアプリが使えなくなるため
- **前提**：`GET` ではデータを変更しないこと。これが崩れると、その `GET` の API が CSRF の穴になる

## 7. トークン方式の利点

ログインを取り消せるかどうかという点では、セッション方式が有利です。トークン方式の強みはセキュリティではなく、**「サーバーが増えても、確認の手間とサーバー間の連携が増えない」**ことにあります。

| 利点 | 何が起きるか | どうしてそうなるか |
|---|---|---|
| ① 本人確認で DB を引かない | リクエストごとの DB へのアクセスが 1 回減る | 署名の検証は、サーバーの中の計算だけで終わるため |
| ② サーバーを増やしやすい | API サーバーを 10 台、100 台と増やしても、ログイン状態を共有する仕組みがいらない | どのサーバーも署名を検証すれば同じ結論になるため |
| ③ 別のサービスでも本人確認できる | ログインを担当するサーバーに問い合わせずに、別のサービスや別の会社の API がトークンを受け入れられる | 公開鍵で署名を検証すれば、発行元に問い合わせなくても「正しい発行元が作ったトークン」だと確認できるため。「Google でログイン」のような仕組みはこの性質を利用している |
| ④ 発行元が止まっても動く | ログインを担当するサーバーが止まっても、発行済みのトークンで他のサービスを使い続けられる | 確認に発行元が関わらないため |

利用者やアクセスが非常に多くサーバーを多数並べる場合や、複数のサービス・複数の会社をまたいで同じログインを使う場合に効果を発揮します。

### 取り消せない弱点の補い方

実際にトークン方式を採用する場合は、次の 2 本立てにするのが一般的です。

- **アクセストークン**：有効期限を 5〜15 分程度に短くする。API はこれの署名だけを検証する（DB は引かない）
- **更新用トークン**：有効期限が長い。DB に記録し、取り消せるようにする。アクセストークンの期限が切れたら、これを発行用の API に送って新しいアクセストークンを受け取る

DB と照合するのは再発行のときだけなので、DB への問い合わせは減ります。ただし、強制ログアウトしても、手元のアクセストークンの有効期限が切れるまでは使えてしまいます。つまり、**取り消しが必要な部分には、結局サーバー側の記録を持たせています。**

また、アクセストークンもリクエストのたびに DB と照合すれば、排他制御や強制ログアウトは即座に効きます。ただしその場合、DB を引かずに済むというトークン方式の利点はなくなり、セッション方式に署名の検証を足しただけの仕組みになります。

## 8. サーバーを増やす（オートスケールする）場合

**サーバーを増やすだけなら、セッション方式でも問題なく動きます。** 条件は、セッションの保存先を API サーバーの外にある共通の DB（RDS、Redis など）に置き、全 API サーバーが同じ保存先を参照することです。

| セッションの保存先 | サーバーが 2 台に増えると | 結果 |
|---|---|---|
| 各 API サーバーのメモリ | サーバー A でログインしても、次のリクエストがサーバー B に振られると、B のメモリには記録がない | **未ログイン扱いになる。** オートスケールと相性が悪い |
| 全サーバー共通の DB | どのサーバーに振られても、同じ DB を引ける | **問題なく動く。** 一般的な構成 |

ただし共通の DB に置いた場合、全サーバーの全リクエストがその 1 か所へ「このセッションは誰か」を問い合わせに行きます。アクセスが非常に多くなると、API サーバーをいくら増やしても、この共通の保存先が混雑して全体の速度を頭打ちにします。トークン方式は各サーバーが自分だけで確認を終えるため、この問い合わせ自体が発生しません。**「サーバーを増やせば増やしただけ処理できる量が伸びる」状態を保てるのが、トークン方式の本当の強みです。** ただし、これが問題になるのはかなり大規模なサービスに限られます。

## 9. 権限（認可）を管理する場合

- **認証**：「ログインしているのは誰か」を確かめること
- **認可**：「その人がこの処理をしてよいか」を確かめること

**自分のアプリの中で権限を管理するなら、セッション方式の方が扱いやすいです。** 権限を変更したとき、すぐに反映されるためです。

**トークン方式の場合**

機能ごとにトークンを分けるのではなく、**1 本のアクセストークンの中に権限を書き込む**のが一般的です。

1. ログインすると、更新用トークンとアクセストークンを受け取る
2. アクセストークンには、ユーザー ID に加えて「管理者」「一般」といった権限が署名付きで書き込まれている
3. API はアクセストークンの署名を検証し、中の権限を読んで、処理を許可するかを判断する。DB は引かない
4. アクセストークンの期限が切れたら、更新用トークンを発行用の API に送り、新しいアクセストークンを受け取る

**結果**：管理者があるユーザーの権限を外しても、手元のアクセストークンには古い権限が書かれたままのため、**期限が切れるまでは外したはずの処理ができてしまいます。**

機能ごとに別のトークンを発行する形は、主に外部のアプリへ限られた権限だけを渡す場合に使います（例：「このアプリにはカレンダーの閲覧だけを許可する」）。

**セッション方式の場合**

アクセストークンのような別の仕組みは作りません。権限は DB のユーザーの情報として持ち、リクエストのたびに確認します。

1. セッションには「誰か（ユーザー ID）」だけを記録する
2. リクエストが来たら、セッションからユーザーを特定し、同じタイミングで DB からそのユーザーの権限を読む（1 回の問い合わせでまとめて取得できる）
3. 権限を見て、処理を許可するかを判断する

**結果**：管理者が権限を外すと、**そのユーザーの次のリクエストから、すぐにその処理ができなくなります。**

## 10. まとめ

| 観点 | 有利な方式 | 理由 |
|---|---|---|
| 強制ログアウト・盗まれたときの無効化 | セッション方式 | DB の記録を消せば即座に無効になる |
| 1 人 1 端末の排他制御 | セッション方式 | サーバーが現在のログインを把握している |
| 権限変更の即時反映 | セッション方式 | 権限をリクエストのたびに DB から読む |
| モバイルアプリへの対応 | どちらでもよい | 差になるのは送り方（Cookie / ヘッダー）であり、方式ではない |
| オートスケール | どちらでもよい | セッションを共通の DB に置けば問題ない |
| 非常に大規模なアクセス | トークン方式 | 共通の保存先への問い合わせが発生しない |
| 複数のサービス・会社をまたぐログイン | トークン方式 | 発行元に問い合わせずに本人確認できる |
