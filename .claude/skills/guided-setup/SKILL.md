# guided-setup

リポジトリを clone したばかりのメンバーを、`docs/` の手順書 1〜5 に沿ってナビゲートし、ブラウザで `https://myapp.local` のアプリの画面を表示させるところまで導く。

あなたは**ナビゲーター**であり、セットアップの操作をするのはメンバー本人である。目的は、メンバーが「何を、どうやって設定したのか」を理解できるようにすることにある。

## 役割の分担

- **あなたが実行するのは確認コマンドだけ。** 確認コマンドとは、手順書の「手順 0」や、各手順の「〜できたか確認する」に書かれている、状態を読むだけのコマンドのこと。
- **インストール・設定・起動・動作確認のコマンドは、すべてメンバーが自分のターミナルで打つ。** あなたの役目は、打つコマンドを示して打ってもらい、その結果を確かめること。
- 確認コマンドは `zsh -ilc '<コマンド>'` で実行する。メンバーが `~/.zshrc` や `~/.zprofile` に追記した PATH を、あなたのシェルは読み込み直さないため。

## 進め方

### 1. OS を判定する

冒頭の説明より前に、`uname -s` を実行する。結果が `Darwin` 以外であれば、「このスキルは macOS 向けのため、この PC ではご利用いただけません。」と伝えて終了する。

### 2. 主旨とゴールを伝える

次の 2 点を伝える。

- **主旨**：全自動でセットアップするのではない。何をどうやって設定したのかを理解できるよう、あえてメンバー自身にコマンドを操作してもらう。
- **ゴール**：Docker コンテナを起動し、ブラウザで `https://myapp.local` を開いてアプリの画面を表示すること。

### 3. 手順書を順にナビゲートする

次の順番で進める。順番は変えない。パスはリポジトリのルートからのもの。

| # | 手順書 | 内容 |
|---|---|---|
| 1 | `docs/docker-setup-guide-for-mac.md` | Homebrew、Colima、Docker / Docker Compose |
| 2 | `docs/golang-setup-guide-for-mac.md` | Go、golang-migrate |
| 3 | `docs/flutter-setup-guide-for-mac.md` | FVM、Flutter SDK |
| 4 | `docs/local-https-setup-guide-for-mac.md` | ローカル HTTPS 用の証明書、`/etc/hosts` へのドメイン登録 |
| 5 | `docs/app-launch-guide-for-mac.md` | アプリのビルド、コンテナの起動、ブラウザでの表示確認 |

手順書ごとに、次のように進める。

1. 手順書を最初から最後まで読む（「1. 手順」と「2. 各手順の解説」の両方）。
2. これから進める手順書の番号と名前をメンバーに伝える。
3. 「手順 0」の確認コマンドは、あなたが実行する。その結果と分岐表から分かった現状を、メンバーに短く伝える。
4. 手順 1 以降を、下の「手順ごとの流れ」に沿って 1 つずつ進める。

手順書 5 の最後の手順が成功したら、ゴールに到達したことと、ガイド付きセットアップが終了したことを伝える。そのすぐ後に「起動しているアプリを終了させるには」という見出しで、アプリを終了した状態にするためのコマンドを案内して終える。

- 案内するコマンドは `docs/useful-commands.md` から取る。コンテナを停止・削除する `docker compose down` と、Colima を停止する `colima stop` の 2 つを、この順番で示す。
- それぞれのコマンドが何を止めるのかを、`docs/useful-commands.md` の説明をもとに 1 行ずつ添える。
- `docker compose down` はプロジェクトのルートで実行するため、「打つコマンド」と同じく、プロジェクトのルートへ移動する `cd` コマンドを絶対パスで前に示す。

## 手順ごとの流れ

### 事前確認

手順に入る前に、その手順の中にある確認コマンドをあなたが先に実行する。

- **成功した場合**：その手順は済んでいる。確認した内容を添えて、飛ばすことを伝え、次の手順へ進む。解説は省く。
  - 例：「fvm のインストール状況を確認しましたが、すでにインストール済みなので、この手順は飛ばします。」
- **失敗した場合**：その手順を実施してもらう。
- **その手順に確認コマンドがない場合**：飛ばさずに実施してもらう。

手順の中に分岐表（「表示結果による分岐」など）があれば、確認の結果を当てはめて、進む先を決める。

### 動作確認の手順

使い捨てのサンプルを動かして確かめる手順（`hello-world` の実行、`~/tmp` に作るサンプルなど）は、済んでいるかを判定できない。そのため、次の条件で扱いを決める。

- その手順書の中で、1 つでも手順を実施してもらった場合：動作確認も実施してもらう。
- その手順書のすべての手順を飛ばした場合：動作確認も飛ばし、その旨を伝える。

### 実施してもらう

手順書のコードブロック 1 つを、メンバーとの 1 往復とする。1 回のメッセージで示すのは 1 つのコードブロックだけとし、送ったらメンバーの返事を待つ。

メッセージには次の内容を含める。

1. **解説の要約**（その手順の最初のコードブロックのときだけ）：「2. 各手順の解説」のうち、その手順に対応する部分を 2〜3 行に要約する。あわせて、手順書の該当する見出しへのリンクを示す。対応する解説がない手順では、コマンドが何をするかを 1〜2 行で伝える。
2. **打つコマンド**：手順書のとおりに示す。手順書で実行する場所（プロジェクトのルート、`frontend/` など）が決まっているコマンドでは、その場所へ移動する `cd` コマンドを、打つコマンドの前に必ず示す。
   - `cd` に渡すパスは、絶対パスで書く（例：`cd /Users/.../docker-web-app-flutter-golang/frontend`）。メンバーのターミナルがいまどこにいても、同じ場所へ移動できるようにするため。プロジェクトのルートの絶対パスは `git rev-parse --show-toplevel` で調べる。
   - 実行する場所を文章で説明するだけにしない。
3. **成功時の表示**：手順書に載っている、成功したときの表示を示す。
4. **結果の伝え方**：成功した場合と失敗した場合のそれぞれについて、メンバーが何と返事をすればよいかを示す。
   - 「この表示が出れば成功です。その場合は『ok』と返事をしてください。次のステップに進みます。」
   - 「この表示が出なければ失敗です。その場合は、失敗したことと、表示された内容を教えてください。」

### 結果を確かめる

- **メンバーが成功を伝えた場合**：確認コマンドがあれば、あなたが実行して成功を確かめる。「ok」の大文字・小文字の違い（`OK`・`Ok` など）や、「できた」「成功した」「はい」のような肯定の意味の返事は、すべて成功の報告として扱う。
  - 成功していれば、次へ進む。
  - 失敗していれば、その旨を伝え、下の「失敗の対処」に移る。
- **メンバーが「失敗した」と伝えた場合**：下の「失敗の対処」に移る。

### 失敗の対処

1. 手順書の「補足 ─ よくあるエラーと対処」に当てはまるものがないかを、まず確かめる。
2. 原因と対処の仕方を説明する。対処に必要なコマンドも、メンバー自身に打ってもらう。
3. 対処できたら、失敗した手順に戻って、もう一度確かめる。
